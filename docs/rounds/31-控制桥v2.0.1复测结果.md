## 3. §4.3 未覆盖：窗口实测只有约 130 ms

这次的探针没能构造出「20 s 不收敛」：

```text
t+8.92s  recovering=1 (until−now=19920 ms)      ← 窗口打开
t+9.05s  recovering=0                          ← 130 ms 后关闭
```

原因不在桥，在宿主：**`Depot.generateDepots` 是同步的**，同一个 server tick 内就把路径算完了。
所以 `isRecovering()` 下一次求值（`urgent` 巡检每 tick 一次，~50 ms）就看到「所有侧线都有路径」，
窗口随即解除。要让它开到 20 s，必须让重建在 20 s 内一直不成功——本线网做不到。

这里顺带修正 v1.9 报告里的一个措辞：那里写的「策略 2 要 ~6 s 才产出路径」是**多策略阶梯**的
累计时间（策略 0 等 3 s → 策略 1 等 3 s → 才轮到策略 2），重建本身是 tick 级的。

超时分支本身的代码是清楚的：

```java
private boolean isRecovering(Depot depot) {          // BridgeService:815
    final Long until = recoveringDepots.get(depot.getId());
    if (until == null) return false;
    if (now > until) { recoveringDepots.remove(depot.getId()); return false; }   // 到期即解除
    …allReady… if (allReady) { recoveringDepots.remove(depot.getId()); return false; }
    return true;
}
```

解除后 `collectBroken()` 会按真实状态重新评估，因此「超时不掩盖」在实现上成立，
但**本轮没有真机证据**。建议用单测覆盖：把 `RECOVERY_WINDOW_MILLIS` 注入成 200 ms，
给一个「重建不产生路径」的假车厂，断言窗口到期后该车厂重新出现在 `pathRecoveryNeeded`。

## 5. 顺带发现：更快的故障复现手法（不用重启）

前几轮制造「持久丢路径」都要「重生成中途停机 + 重启」。本轮试出更快的一条：

```text
1) set_platform(停场车, 跨线路站台)     → 策略 0 清空本侧线路径
2) 等 3.2 s，车被重建（新 id），再对新车发同一条命令
   → 第二次的 PathSnapshot 已经是空路径
3) 两次尝试都失败（跨线路确实产不出路径）→ 回滚把空路径写回去
   → 该侧线持久丢失，直到车厂重建；全程不需要重启
```

实测（regen 关闭时）：约 6 s 后 `need=1`、`lostVehicles=[a37272]`，`/mtbridge audit` 命中该车厂，
此后一直保持，直到执行 `/mtbridge recover`。以后要复测 advisory / 恢复链路，用这条最快。
