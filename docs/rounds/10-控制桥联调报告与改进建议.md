# 10 · 控制桥联调报告与改进建议

对象：工作区内的控制桥模组（`mtbridge`）与外部调度服务（`tsc-dispatch`）。
环境：真实 Forge 专用服务端，Minecraft 1.20.1 / Forge 47.4.23 / MTR **4.0.5**（FORGE 构建）。

---

## 1. 结论摘要

| 项目 | 结果 |
|---|---|
| 桥 HTTP 面（capabilities / health / state / command） | ✅ 可达，令牌鉴权生效（无 token → 401） |
| 服务 ↔ 桥协议 | ✅ 服务按真实线格式改造后，桥正确解析并落到 MTR 模拟线程 |
| 桥定位 TSC 模拟器 | ❌ **首次启动失败**（`simulators located: 0`），复现 100%，已定位并验证修复 |
| 服务降级 | ✅ 桥 `ready=false` 时自动落到只读通道，不崩、不发假指令 |
| 决策级（有车流）验证 | ⚠️ 未覆盖：测试世界没有任何 MTR 线网（0 车站 / 0 线路 / 0 车辆） |

一句话：**桥的协议设计是对的，但启动时序有一个致命竞态，导致它在真机上从未真正可用；服务侧已按真实桥能力重写决策分支，并验证了降级路径。**

## 2. 服务侧依据真实桥做的改造

真实桥只提供 4 种指令：`set_platform`、`deploy_train`、`return_to_depot`、`dwell_control`。
这与服务原先假设的“可随时改任意运行中列车的路径”有本质差别——桥的源码写得很清楚：
**列车一旦在运行，路径在整个班次内冻结**，改台只能等它回到侧线。

| 桥的真实语义 | 服务改造 |
|---|---|
| `set_platform` 对运行中列车返回 `DEFERRED`（挂 30 分钟意图） | 只有 **停在场站（`inDepot`）** 的列车才发 `set_platform`；运行中列车改发 `dwell_control`（压站），避免“半小时后才生效”的幽灵指令 |
| `dwell_control` 秒数 0=释放、>0=延长、<0=无限 | 新增 `HOLD` → `dwell_control` 的线格式映射，秒数由站台释放时刻算出（10–120 s） |
| `return_to_depot` 目标 `sidingId`，且对运行中列车同样挂意图 | `RETURN_TO_DEPOT` 参数改发 `sidingId`；容量约束在服务侧先过滤，不做“必然被拒”的下发 |
| `deploy_train`（无此服务指令） | 新增 `Command.Kind.DEPLOY`，为后续“发车避让”预留 |
| `capabilities.features` 按需变化，`ready` 反映世界是否加载 | 执行器能力**每次调用重新解析**；桥未就绪 → 不视为可用 |
| 全部接口走 `Authorization: Bearer` | 桥连接使用独立 HTTP 客户端（独立超时 + 令牌），不再复用 TSC 只读客户端 |
| 报文 `{kind, vehicleId, args, key}` | 适配器只发这 4 个字段；`seq/precondition/reason` 作为附加字段被桥忽略（向前兼容） |

另外两处由真机数据倒逼的修正：

- **站台归属**：桥的 `vehicles[].stationId` 是“当前所在站”，`nextPlatformId` 是“下一个停靠台”，两者不同帧。
  服务改为用 `platforms[].stationId` 反查下一站台所属车站，否则站台冲突检测会分错组。
- **停场列车不占台**：`inDepot=true` 的列车只是“打算去某站台”，并不占用它；占用表跳过这些车，
  否则它们会把站台锁死到永远。

## 3. 真机测试记录

### 3.1 启动（第一次，原始 jar）

```text
[21:00:46] [Server thread/INFO] [mtbridge/]: simulators located: 0 (none)
[21:00:46] [Server thread/INFO] [mtbridge/]: bridge listening on 127.0.0.1:8889
[21:00:47] [MinecraftTransitRailway/]: Found available port: 8888
[21:00:47] [TransportSimulationCore/]: Server started with dimensions
             [minecraft/overworld, minecraft/the_end, minecraft/the_nether]
```

注意最后一行：**维度顺序是 overworld → the_end → the_nether**，与直觉相反；
服务配置里的 `dimensions[].index` 必须照抄这个顺序，不能按 id 猜。

### 3.2 桥接口

```text
GET /dispatch/v1/capabilities        (Bearer)
{ "protocol":1, "features":["set_platform","deploy_train","return_to_depot","dwell_control"],
  "dimensions":0, "ready":false }

GET /dispatch/v1/health
{ "ok":false, "ready":false, "dimensions":0, "executed":0, "failed":0, "deferred":0,
  "pendingIntents":0, "lastError":"" }

GET /dispatch/v1/state?dimension=0   → HTTP 503 no_simulator
GET /dispatch/v1/capabilities (无 token) → HTTP 401
```

### 3.3 服务面对坏桥的行为（fail-safe）

```text
$ GET /v1/status
health=OK  bridgeOnline=false  actuator=observe  source=tsc-stock-http
dimension= minecraft/overworld@0: OK / INCOMPATIBLE

$ GET /v1/channels .bridge
{ "ready": false, "health": { "ok": false, "dimensions": 0, ... } }
```

即：**桥不可用 → 服务照常读 MTR 自身的 TSC HTTP，不伪装能控制**。
这也验证了“能力降级”不是纸面设计。

### 3.4 定位与修复验证

读取发布版 jar 的方法签名，确认根因不是反射写错：

```text
javap org.mtr.mod.Init     → private static org.mtr.core.Main main;
javap org.mtr.core.Main    → private final ObjectImmutableList<Simulator> simulators;
```

字段类型、容器类型都对得上，所以问题只可能是 **取字段的时刻 `main` 还是 null**：
`ServerStartedEvent` 不保证订阅者顺序，MTR 在自己的监听里才 `new Main(...)` 并赋值，
桥的监听先跑，`locate()` 取到 null，然后**再也没有重试**（`locator` 被覆盖成 none）。

在**临时副本**上打 3 行补丁验证（未改动原工程）：

```java
// MtBridgeMod.onServerTick
if (!host.ready()) {
    host.attach(ServerLifecycleHooks.getCurrentServer());   // 宿主初始化完成前持续重试
}
```

重启后：

```text
[21:03:50] [mtbridge/]: simulators located: 0 (none)      ← 事件期仍是 0（正常）
GET /dispatch/v1/health → { "ok":true, "ready":true, "dimensions":3 }
GET /dispatch/v1/state?dimension=0 → 200 { serverTime, stations:[], platforms:[], vehicles:[] }
```

### 3.5 端到端（服务 → 桥 → MTR 模拟线程）

```text
服务 /v1/status:  source=tsc-control-bridge  vehicleTelemetry=true
                  bridgeOnline=true  actuator=bridge

服务 /v1/command (未知车辆):
  { "type":"MANUAL", "status":"SKIPPED", "outcome":"vehicle no longer observed" }
      ← 服务拒绝为“没见过”的车下指令，这是设计上的保护

用服务完全相同线格式直连桥:
  POST /dispatch/v1/command?dimension=0
  {"kind":"set_platform","vehicleId":"999999","args":{"platformId":"...0001"},"key":"probe-1"}
  → { "ok":false, "outcome":"rejected", "message":"no such train", "applied":false, "retryable":false }
  {"kind":"dwell_control","vehicleId":"999999","args":{"seconds":30},"key":"probe-2"}
  → 同上

桥 /health: { "executed":0, "failed":2, "lastError":"no such train" }
```

说明：桥正确解析了服务的报文、在模拟线程上执行、并在 MTR 里查车失败后返回结构化拒绝。
**协议层是通的**；缺的只是“世界里真的有车”。

## 4. 对控制桥模组的改进建议

### P0 · 阻断级（真机复现，必须修）

**4.1 启动时序竞态导致桥永远不可用**

现：`ServerStartedEvent` 里 `host.attach()` 取 `Init.main` 可能为 null，之后不再重试。
改（二选一，建议都做）：

- 在 `ServerTickEvent` 里重试直到 `host.ready()`（已验证可行，3 行）；
- 或给监听加 `EventPriority.LOWEST`，确保 MTR 先赋值；
- 并在重试期间每 5 s 打一条 INFO（“等待宿主初始化 n/12”），12 次仍失败则明确 WARN 并停止重试，
  而不是像现在这样静默地 `ready=false` 一整个会话。

**4.2 只 tick 了维度 0**

```java
final Simulator simulator = host.simulator(0);   // 1..n 维度的意图与压站永远不执行
if (simulator != null) service.tick(simulator);
```

既然是“每维度独立”，`tick` 必须遍历 `0..dimensionCount()-1`。
否则地下列车回场的意图永远不会被处理——而这恰恰是桥最核心的能力之一。

### P1 · 语义正确性

**4.3 `set_platform` 对运行中列车的意图最长挂 30 分钟**
类注释说“会等列车回侧线再重建”，但 30 分钟的意图意味着一次早上做的决定，中午才生效。
建议：命令里带 `ttlSeconds`（默认 120），或按“列车跑完当前一趟的预计时间”计算上限；
并在 `/health` 里暴露 `intents: [{vehicle, kind, ageSeconds, deadline}]`，让调用方看得见陈旧的意图。

**4.4 `RETURN_TO_DEPOT` 完全忽略 `target`**
`dispatch()` 里对 `RETURN_TO_DEPOT` 只做 `parkAndHold`，`command.target()`（sidingId）从未使用。
要么真正实现“停到指定股道”，要么把 `sidingId` 从契约里删掉——现在它是个会误导调用方的参数。
（服务侧目前照发，因为宁可参数多余，也不要在协议里说谎。）

**4.5 遥测字段缺三样，逼着调用方猜**

| 缺的字段 | 后果 | 建议 |
|---|---|---|
| `serviceStart` / 本次班次开始时间 | 服务只能用“首次观测时刻”近似，重启即重置，定时回场规则失真 | 由 `vehicle` 的出发时刻推出并下发 |
| `passengers` | “载客中不得中途回场”这条边界无法在服务侧成立 | 从 `vehicleCars` 汇总 |
| `departure` | 现在恒等于 `now`，占用窗口只能靠服务端补 20 s | 用 `eta + 站台 dwell` 推算 |

**4.6 `stationId` 与 `nextPlatformId` 是两个坐标系**
一个对象里同时给了“当前所在站”和“下一个停靠台”，调用方很容易把两者当同一帧。
建议显式命名：`currentStationId` / `nextStationId` / `nextPlatformId`，
并在 `/dispatch/v1/capabilities` 里写清 `semantics` 版本。

**4.7 `dwell_control` 无限压站缺少兜底**
`seconds < 0` 表示无限期压站，只有再发一条 `seconds=0` 才释放。
若调度服务崩溃，列车会永久停摆。建议：加 `maxHoldSeconds`（如 600），到期自动释放并记录事件。

### P2 · 协议与运维

- **幂等缓存把 `DEFERRED` 也缓存了 600 s**：意图后来真正生效时，调用方重试仍会拿到旧的 DEFERRED，
  无法区分“还在排队”和“刚刚完成”。建议只缓存终态（APPLIED/REJECTED/FAILED），
  DEFERRED 改为可查询的意图状态。
- **capabilities.dimensions 只是数量**：给不出 id/index，调用方无法校验自己的维度配置。
  本次真机就踩到“overworld → the_end → the_nether”的顺序陷阱。建议返回
  `[{index, id}]`，id 用与 TSC 一致的 `minecraft/overworld` 形式。
- **state 无版本/无 ETag**：2 s 轮询全量重算。建议加 `version` 或 `?since=`，允许 304。
- **503 缺 `loading` 标记**：`no_simulator` 无法区分“世界没加载”和“桥坏了”。建议 `{error, loading:true}`。
- **鉴权用 `String.equals`**：改成 `MessageDigest.isEqual` 做定时安全比较；且当 `bindAddress` 非回环时
  若 `token` 为空应拒绝启动，而不是裸奔。
- **HTTP 线程只有 2 个且同步等 `future.get(2500)`**：状态轮询与指令并发时会互相饿死。
  建议 4–8 线程，或把 `state` 改为异步响应（先 202 再回调）。
- **可测试性**：加一个 `dryRun` 开关，让没有世界的环境也能演练指令链路（本次服务自检就是靠 mock 桥做的）。

## 5. 覆盖范围与后续验证

**已验证**：桥 HTTP 面、令牌鉴权、协议线格式、命令落到 MTR 模拟线程、服务侧降级与恢复、
维度顺序处理、端口探测（MTR 8888 实际监听）。

**未验证**：有车流时的选台/压站/回场决策。原因是测试世界 `world/mtr/minecraft/overworld/*`
全部为空（0 车站、0 线路、0 车辆），无法无头构造 MTR 线网。

要在真机覆盖决策级，需要其中一种条件：

1. 提供一个含 MTR 线网的存档（车站/站台/线路/车厂/列车齐全）；
2. 或用创造模式在游戏内搭一条最小线网（2 站 1 线 1 车厂 2 车），再重启服务观察 `/v1/decisions`；
3. 或让桥支持“注入合成列车”（仅测试用），这样无存档也能跑通。

## 6. 服务侧仍存在的限制（诚实清单）

1. **无车流时不会产生任何决策**，健康度只能反映“传输通、拓扑空”。
2. `REROUTE` 在真实桥上不可执行（桥无此能力），会一直以 `ADVISORY` 呈现；
   若桥将来提供 `reroute`，服务会自动启用，无需改代码。
3. `serviceStart` 缺失时用首次观测时间兜底，**服务重启会让计时归零**——建议桥补该字段（见 4.5）。
4. 决策级只有在 §5 任一条件满足后才能做真机回归；当前的 78 条断言覆盖的是协议、算法与降级逻辑，
   不等于“真车验证”。
