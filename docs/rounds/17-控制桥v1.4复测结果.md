## 0. 结论

```text
清单结果： 1 ❌   2 ⏭（无法到达）   3 ❌   4 ❌   5 ✅
```

- **P0（dwell 崩服）没有回归**，第 5 项通过。
- **P1 仍未解决**：策略 0 启动后，尝试记录在 **500 ms 内无声消失**，既没升级到策略 1，

- 因此第 2 项（打开 `allowDepotRegeneration`）**在逻辑上不可达**：代码要求先跑满 3 s 才会升级到策略 2，
  而记录根本没活到 3 s。
- 本轮新增的三个观测点：`routeDiag` 能出现（但一闪而过），`lastTickError` 为空，
  `/health` 里 **没有** `lastTickError` 字段。

## 1. 逐项结果与证据

### [1] 停场车 `set_platform` 换台 — ❌ 失败

```text
before: id=330077 siding=9d163c planned='4ad4105fad8390aa'
POST set_platform(-> 430A53)
→ { "outcome":"deferred", "message":"route strategy 0 started: generateRoute(platform, null, -1)" }

routeDiag（t+0，一次性抓到）:
  { "siding":"a37272e024f03a0c", "platform":"9a0cfdf403e9c82e",
    "strategy":0, "strategyName":"generateRoute(platform, null, -1)", "startedAt":1792684644460 }
t+500ms 起: routeDiag=[]        ← 500 ms 内消失，未升级、未失败
planned='0' pathReady=False      ← 一直保持
health: executed=0 failed=0 deferred=4 tickFailures=1 lastError=''
```

关键点：`routeDiag` 本身是对的（侧线 id 与 `depots[].sidingIds` 完全一致、平台正确），
说明`trackRoute` 注册成功；问题出在 tick 里的处理阶段。三个移除点分别会带来
`executed++`（路径就绪）、`failed++`（策略耗尽）、`recordTickError`（异常），
**本次一个都没有发生**——记录是被“静默”移除的，现有埋点无法区分是哪一条。

### [2] 打开 `allowDepotRegeneration` 后重试 — ⏭ 不可达

策略升级的条件是 `now < attempt.nextAt()（+3 s）时继续等待`，到达后 `nextStrategy=1`，
再过 3 s 才考虑 `nextStrategy=2`。而记录在 500 ms 内就消失了，**永远走不到策略 2**。
所以本轮没有做“改配置—重启—重试”，因为那不会改变任何结果；先修 §1[1] 才谈得上。

### [3] 停场车 `deploy_train`（无目标）— ❌ 失败

```text
deploy_train(859109…) → deferred "departure queued"
t+1s…t+5s: onRoute=False speed=0.0 pathReady=False next=000000
health: failed=0, deferred=2, intents=[]
```

与 v1.3 一致：车不动，也不报错。

### [4] `deploy_train(car, platform)` — ❌ 失败

```text
deploy_train(368391…, 9A0CFD)
→ deferred "path regenerated; departure queued on siding 6b6eacc355ec212f …"
routeDiag: t+0 = [s0] → t+500ms 起 = []
t+2s…t+3.5s: planned='0' pathReady=False
≈15 s 后：pendingIntents 清空，tickFailures 1→2，lastTickError 仍为 ''
```

侧线意图最终按 deadline 过期（“path regeneration never settled; departure abandoned”），
这一步会 `tickFailures.incrementAndGet()` 但**不写 `lastTickError`**，所以外部只看到一个 +1 的计数。

### [5] `dwell_control` 回归 — ✅ 通过

```text
dwell_control(20s) → applied "dwell hold set"
holds=[{vehicle:-57073…, remainingSeconds:17}]
25 s 后: holds=[], tickFailures 未增加（保持 1）, 无崩溃报告
```

## 3. 静态代码定位（供你直接对照）

`BridgeService.processRouteAttempts` 只有三个移除点：

```java
if (siding == null) { routeAttempts.remove(...); continue; }            // ① 无埋点
if (GameActions.routeSegments(siding) > 0) { routeAttempts.remove(...);  // ② executed++
    fire(... applied "path ready via 策略N"); executed.incrementAndGet(); }
if (nextStrategy >= ROUTE_STRATEGIES || blockedByConfig) { remove;      // ③ failed++
    fire(... failed); failed.incrementAndGet(); }
...
catch (Throwable t) { routeAttempts.remove(...); recordTickError("route: " + t.getMessage()); } // ④
```

观测到的组合是“记录消失 + executed/failed 都没涨 + tickFailures 不变”，
与 ①（静默）吻合，但与 ②③④ 都不吻合。**请在 ① 处补一条 WARN（sidng id + 原因）**，
这是目前唯一能解释该现象的分支。

补充两个可能的原因，按可能性排序：

1. `attempt.sidingId()` 与 `simulator.sidingIdMap` 的键**不是同一个 id 空间**。
   注意同文件 402 行用 `sidingIdMap.get(intent.sidingId())` 是成功的（意图能处理到 deadline），
   所以更可能是 `trackRoute` 传入的 `siding` 不是同一个对象/同一个 id。
2. `routeSegments` 之外的某个调用抛了异常，但异常被 ④ 之外的地方吞掉（例如 `fire` 的监听器）。

## 4. 另一件必须提醒的事：路径被清空且不恢复

本轮开始时四列车都有有效计划台（`4ad410…` / `9a0cfd…`）；每触发一次重生成，对应侧线就变成 `"0"`。
四次探测后，**全部四列车 `plannedFirstPlatformId="0"`**。

重启服务器后（同一份世界文件）依然是 `"0"`：

```text
磁盘对比：world/mtr/.../sidings 下 5 个文件与原始存档**字节大小完全一致**（1974 / 4707 B）
→ 不是把存档写坏了，而是运行时路径未重新生成，重启也没有自愈
```

`Siding.generateRoute` 的第一条指令会清空侧线内的车辆与路径（v1.2 报告已用字节码确认过车辆部分），
**先清后建、建不出来就什么都不剩**。建议：

- 调用前快照 `pathSidingToMainRoute / pathMainRoute`，生成后仍为空则**回滚**；
- 或在生成前先做一次“可达性预检”，不可达就不要清；
- 至少要在 `/state` 里明确报 `pathLost: true`，别让调用方以为“只是没发车”。

## 5. 建议的下一步（按顺序）

1. **给三个移除点各补一行日志**（含 siding id、策略、移除原因），再跑一次同一个命令——
   现在缺的不是功能，是可解释性；
2. 修掉“静默移除”，让策略 1/2 真的有机会执行；
3. 加**路径快照/回滚**，避免再出现“探测一次就毁掉一条侧线”；
4. 补 `/health.lastTickError`，并让 402 行那条 intent 过期也写入 `lastTickError`；
5. 第 3/4 项（发车）等 1–2 修好后用 `plannedFirstPlatformId != "0"` + `pathReady=true` 验收。

**结论：P0 稳定，P1 卡在“重生成尝试在 500 ms 内被静默丢弃”，
在补上移除点日志之前，策略升级与发车链路都无法验证，也无法远程诊断。**
