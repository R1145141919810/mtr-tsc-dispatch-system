## 1. 关键证据

### [1] 原始存档是完好的

用用户存档的**全新副本**启动，四列车全部有有效计划台：

```text
id=109282 siding=0a7783 planned='4ad4105fad8390aa' pathLost=False
id=-26683 siding=6b6eac planned='9a0cfdf403e9c82e' pathLost=False
id=563935 siding=a37272 planned='9a0cfdf403e9c82e' pathLost=False
id=386869 siding=9d163c planned='4ad4105fad8390aa' pathLost=False
health: tickFailures=0 lastTickError='' routeDiag=0
```

上一轮被清空的是**测试副本**，不是你的存档。§5 的恢复操作**不需要做**。
同时 `/health` 已经带上 `lastTickError` 与 `routeDiag`。

### [2] 可达目标：策略 0 就成功

```text
set_platform(386869 → 430A53)
→ deferred "route strategy 0 started: generateRoute(platform, null, -1)"
t+1s diag=s0  planned='0'       pathLost=True
t+3s diag=[]  exec=1  planned='430a5317fa60e8b1'  pathLost=False   ← 成功
```

清单预期是“3 s 升级、6 s 失败回滚”，实际是**策略 0 在 ~3 s 内就产出了路径**
（`generateRoute` 是异步的，前 2 s 内车处于暂时无路径状态，`pathLost` 会短暂为 true）。
这比预期更好：不需要升级，也没有触发回滚。

### [2b] 不可达目标：升级 + 回滚（本轮核心）

用“线路 2 的侧线 → 线路 1 的平台”制造物理不连通：

```text
set_platform(563935 → 430A53)
t+1..2s diag=s0   planned='0'  pathLost=True
t+3..5s diag=s1   planned='0'  pathLost=True      ← 升级生效
t+6s    diag=[]   failed=1     planned='9a0cfdf403e9c82e'  pathLost=False   ← 回滚成功

lastError="path generation produced nothing; depot regeneration is disabled
           (allowDepotRegeneration=false); previous path restored"
```

三点全部达标：**升级可见、失败可见、旧路径被写回**（planned 回到原值，侧线没有被毁）。
这正是上一轮报告 §4 要求的能力。

### [3] 策略 2：车厂级重建

先让“全部四条侧线都无路径”（重启后复现了上一轮的现象，见 §3），再打开 `allowDepotRegeneration=true`，
对线路 2 的车发一次 `set_platform`：

```text
t+1..2s diag=s0   planned='0'
t+3..5s diag=s1   planned='0'
t+6s    diag=[]   exec=1   planned='9a0cfdf403e9c82e'
结果：depot 2 的两条侧线同时恢复（6b6e 与 a37272 均 planned=9a0cfd，车辆 id 变化）
      depot 1 的两条侧线保持 pathLost=True（未被重建，符合预期）
```

说明策略 2 在真机上可执行，且**确实会重建整个车厂**（车辆被重新生成、id 变化），
与文档的“破坏性”描述一致。

### [4a] deploy（无目标）

```text
deploy_train(433227) → deferred "departure queued"
t+1s onRoute=True speed=4.0
t+5s onRoute=True speed=16.7
随后 telemetry 补齐：route=639871 next=b35e44 station=ce1d84
```

**车真的开出去了**，而且一旦驶上正线，`routeId/nextPlatformId` 就正常回填
（离站初期为 0 属于“还在侧线→正线连接段”，不是缺陷）。

### [4b] deploy（带目标）— 唯一剩下的缺口

```text
deploy_train(-26683, 9A0CFD)
→ deferred "path regenerated; departure queued on siding 6b6eacc355ec212f"
t+3s 起 diag=[]（路径已就绪）  planned='9a0cfdf403e9c82e'  ← 目标正确
t+3..20s run=False speed=0                                ← 但没发车
health: exec=4 failed=0 pendingIntents=0 lastError=''
随后手动再发一次 deploy（无目标）→ 1 s 内 onRoute=True
```

即：**重建正确、排队发车没有生效**，但车本身是可发车的。怀疑是侧线意图取到的车辆对象
在重建后已不是当前实例（或 `startUp` 作用在了旧对象上）。运维/调度侧的规避很直接：
先 `set_platform`（或 `deploy` 带目标）等路径就绪，再补一次 `deploy`（无目标）。

## 2. 仍然存在的一个数据风险（非本轮修复范围）

上一轮报告 §4 的“路径被清空且重启不恢复”在本轮**再次复现**，而且是在 `rollback` 已生效的版本上：

```text
本轮第一次重启前：四条侧线 planned 全有效
做过 2 次 set_platform + 2 次 deploy 后重启：四条全部 planned='' / pathLost=True
（depot 2 后来靠策略 2 恢复；depot 1 仍为 pathLost）
```

区别在于：**回滚只保护“失败”的重生成；成功的重生成如果紧接着发生存档，路径仍可能在重启后丢失。**
建议：

1. 重生成成功后调用一次 `writePathCache()`（Siding 里有这个方法），或在存档前确保路径已落盘；
2. 调度服务侧把 `pathLost=true` 当成硬阻断：该维度不再发任何依赖路径的指令，只出 advisory；
3. 运维侧保留“一条命令恢复”：对车厂执行一次策略 2（本轮已验证有效）。

---

## 3. 给服务侧的一个直接结论

本轮验证说明：**只要 `pathLost=false` 且 `plannedFirstPlatformId ≠ "0"`，发车链路就是通的**。
因此服务侧应把这两项作为“可调度前置条件”：

- 车辆 `pathLost=true` → 视为不可调度，直接跳过选台/发车，并在 `/v1/decisions` 里说明原因；
- 车辆停场且 `plannedFirstPlatformId="0"` 但 `pathLost=false` → 处于重生成窗口内，等下一轮再看。

这条规则可以把“重建窗口内的误判”挡在决策之外，也正好对应本轮观察到的 t+1..2s 现象。

---

## 4. 复测结论

- **v1.5 达成了本轮目标**：移除不再静默、失败可回滚、诊断字段齐全、策略 2 可执行。
- **发车链路只差最后一环**：带目标 deploy 的自动发车；补一次普通 deploy 就能发车。
- **路径持久化仍是隐患**，建议下轮把 `writePathCache` / 存档时序纳入范围。
- 环境已还原：测试服务端停止、模组与空世界恢复、用户存档未改动。
