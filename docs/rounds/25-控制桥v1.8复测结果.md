# 25 · 控制桥 v1.8 复测结果（真实服务端）

环境：Forge 47.4.23 · MC 1.20.1 · MTR **4.0.5** · mtbridge **1.8.0**（90,931 B）· tsc-dispatch 1.0.0（223,572 B）
世界：用户存档副本（3 站 / 12 站台 / 4 独立轨道 / 2 车厂 / 4 侧线 / 4 车，另有 1 条未挂车厂的 403 B 侧线）
依据：docs/24-车厂级路径体检与恢复（控制桥 v1.8）.md §5

## 0. 结论

```text
§5.1 /mtbridge audit 列出 depot 2          ✅ 通过（侧线 id、停场车数都对）
§5.2 /mtbridge recover 修复并可用          ✅ 通过（planned 恢复、发车复测通过）
§5.3 allowDepotRegeneration 自动修复       ✅ 通过（开机首个巡检周期内，日志 + lastError 都有）
§5.4 persistPath 读回校验                  ✅ 存在且生效；本轮 ok=true，未触发失败分支
§4   events.seq 单调递增                   ✅ 通过（会话内单调；跨重启归零，需文档化）

❗ 新发现 ①（P1）配置带 BOM → 静默回落默认值：token 失效、allowDepotRegeneration 失效
❗ 新发现 ②（P1）pathRecoveryNeeded 被逐维度覆盖 → 实际恒为空，§3.1 的对外 advisory 无效
❗ 新发现 ③（P1）/mtbridge audit、recover 只取 simulator(0)，维度顺序一乱就打错车厂

❗ 结论修正：单侧线重生成 / 车厂重建 都不会让路径在重启后丢失（4 次重启验证）；
   真正能稳定复现的故障是「重生成过程中停机」，且影响是【侧线级】而非车厂级。
```

## 1. 基线：原始存档本身是健康的

第一手测量（全新副本、首启、未做任何操作）：

```text
-8569854173813228684 depot=1（线路头）  siding=0a7783 planned=4ad4105fad8390aa lost=false
-8988211246448445112 depot=2（线路中）  siding=6b6eac planned=9a0cfdf403e9c82e lost=false
2613289200548223757  depot=2（线路中）  siding=a37272 planned=9a0cfdf403e9c82e lost=false
4580135611878090531  depot=1（线路头）  siding=9d163c planned=4ad4105fad8390aa lost=false
```

4 条侧线 planned 全部非零、`pathLost=false`。所以 v1.7 报告里那种「重启后 depot 2 两条侧线全丢」
不是存档自带的，而是在**某一轮测试过程中**被造出来的。这一条改变了本轮排查方向。

## 2. 实验矩阵：到底什么操作会让路径丢

| # | 操作 | 重启后 | 结论 |
|---|---|---|---|
| A | 单侧线重生成（策略 0 失败 → 策略 1 成功）+ 正常 `stop` | 全部 `lost=false` | 不会丢 |
| B | 车厂重建（策略 2 `Depot.generateDepots`）+ 正常 `stop` | 全部 `lost=false` | 不会丢 |
| C | **重生成过程中停机**（策略 0 已清路径、新路径未生成时 `stop`） | 该侧线 `planned='' lost=true` | **可稳定复现** |
| D | `/mtbridge recover` 修复后重启 | 全部 `lost=false` | 修复可持久 |
| E | 自动修复后重启（regen 开关保持） | 全部 `lost=false` | 修复可持久 |

### A · 单侧线重生成（正常停机）

```text
t+0.0s  deploy_train(car, 9a0cfdf403e9c82e) → DEFERRED 路径重生成
t+3.1s  set_platform APPLIED  "path ready via generateRoute(platform, platform, 0), persisted"
t+4.8s  inDepot=false, speed=1.8      ← 离场
t+5.6s  deploy_train APPLIED  "departed and verified on route"
t+8.8s  speed=16.7（满速）
```

重启后：depot 2 两条侧线 planned 都是 9a0cfd…，`lost=false`；被重建的车（8150…）**带着 routeId 继续在线上跑**。

### B · 车厂重建（策略 2，正常停机）

```text
t+0.8s  set_platform DEFERRED "route strategy 0 started"   a37272 → planned=0 lost=true（清路径中）
t+3.2s  车被重建（id 变化）
t+6.1s  set_platform APPLIED  "path ready via Depot.generateDepots([depot]), persisted"
        车厂内两台车全部换 id（1015… / 2430…），两条侧线 planned 均恢复
```

重启后：仍然健康。**策略 2 的结果是能活过重启的**，这一点很重要——`recover` 用的就是它。

### C · 重生成过程中停机（本轮唯一可复现的故障）

复现配方（给桥方自测用，3 步）：

```text
1) set_platform(某停场车, 另一条线路的站台)   → 策略 0 立即清空本侧线路径
2) 1.5 s 内 stop 服务端                        → 新路径还没生成就被存档
3) 重启 → /mtbridge audit                      → 该车厂被列出
```

实测结果：

```text
重启后 3153734704158645739 depot=2（线路中）siding=a37272 planned=0 lost=true
其余 3 条侧线 planned 正常，depot 1 完全不受影响
```

**影响范围是侧线级**：同一车厂的另一条侧线（6b6eac）是好的。这与 v1.7「车厂级传染」的判断相反。

## 3. §5.1 体检：通过

```text
/mtbridge audit →
[{depot=2（线路中）, depotId=64542daa4ef67d13, sidings=[a37272e024f03a0c], parkedTrains=2}]
```

要的三样都在：车厂名、车厂 id、丢路径的侧线 id；外加停场车数。
健康时输出 `all depots have paths`。

### 但 §3.1 承诺的对外字段没有生效（P1）

`/health.pathRecoveryNeeded` 在同一时刻返回 `[]`。六步实验证明它不是偶发：

```text
A) 刚开机（某侧线已丢路径）      /health.pathRecoveryNeeded = []
B) rcon: mtbridge audit           → 正确列出 depot 2
C) 紧接着 /health                = [{depot=2（线路中）, sidings=[a37272…], parkedTrains=2}]
D) 等过一个 10 s 巡检周期 /health = []            ← 被冲掉了
E) rcon: mtbridge audit           → 仍然列出 depot 2（故障没变）
F) 紧接着 /health                = [{…}]           ← 又被填上
```

原因在 `MtBridgeMod.auditDepots()`：它按维度循环调用 `service.auditDepots(simulator)`，
而 `BridgeService.auditDepots()` 每次都用本维度结果**整体覆盖** `pathRecoveryNeeded`。
本轮维度顺序是 overworld, the_end, the_nether，最后一维（下界）没有车厂 → 返回空表 → 覆盖成空。

所以 §3.1 写的「外部（含调度服务）可以据此只出 advisory」目前拿不到数据。

## 4. §5.2 手动恢复：通过

```text
/mtbridge recover        → recovered 1 depot(s)
/mtbridge audit          → all depots have paths
depot 2 两条侧线          → planned=9a0cfdf403e9c82e，lost=false
depot 2 车辆              → −6106463906745759273 / −8935103819185173272（全部换 id）
depot 1 车辆              → 未变（−8569… / 4580…）
```

第二次复测（另一个 boot）同样：`recovered 1 depot(s)` → 两条侧线 planned 恢复。
健康世界上执行是安全的：`recovered 0 depot(s)`，不会顺手把好车厂拆了。

### 恢复后的可用性验证

对一个刚恢复的侧线直接发车：

```text
t+0.0s  deploy_train → DEFERRED
t+3.2s  "path ready via generateRoute(platform, platform, 0), persisted"
t+4.8s  inDepot=false speed=1.8
t+5.6s  "departed and verified on route"
t+8.8s  speed=16.7
```

恢复出来的车厂是**真的能用**，不只是 audit 好看。

### 缺的东西

`recover` / `autoRecover` 走的是 `regenerateDepotQuietly()`，不经过 `service.execute()`，所以：

- `/health.events` 里没有任何记录（seq 不增长）；
- `lastPersist` 保持 `{}`；
- `/mtbridge status` 的 executed/failed 都是 0。

运维在事后回看时，恢复动作是「隐形」的。建议补一条事件 + 一个 `lastRecovery` 字段（见 §7）。

## 5. §5.3 自动修复：通过

把 `allowDepotRegeneration` 打开、带着故障重启：

```text
t+0.1s … t+8.2s   755885529936057812 planned=0 lost=true        ← 故障可见
t+10.2s           748618453943134001 planned=9a0cfdf403e9c82e lost=false
                  7795326491133846118 planned=9a0cfdf403e9c82e lost=false
```

`/health.lastError`：

```text
auto-recovered depot 2（线路中） (paths were missing)
```

服务端日志（WARN，一分钟最多一条）：

```text
depots with missing paths: [{depot=2（线路中）, depotId=64542daa4ef67d13,
  sidings=[6b6eacc355ec212f], parkedTrains=3}]
  (auto-recovered 1, allowDepotRegeneration=true); run '/mtbridge recover' to rebuild them
```

时点：开机后**首个 200 tick 巡检周期内**（≈10 s），早于任何外部调用。
修复后重启仍然健康（E），说明自动修复不是「每次开机都要重做一遍」的补丁。

## 6. §5.4 与 §4

### persistPath 读回

代码落实了：`writePathCache()` 之后再查 `routeSegments(siding) > 0` 才算 true。
本轮 4 次重生成全部 `ok=true`、`persistFailures=0`，失败分支没被触发——所以 §5.4 的后半句
（失败时 ok=false + lastError 有原文）属于「未验证的成功路径」，不是「已验证」。

### 关于 §6「宿主为什么不采用 writePathCache」——本轮有更硬的解释

用 SHA1 逐字节比对重生成前后的存档：

```text
depots\13\64542DAA4EF67D13     3413 B → 3413 B   SHA1 变了
  差异字节只有 3 个（偏移 179–181），上下文是：
  … lastGeneratedMillis <3 bytes> lastGeneratedStatus=SUCCESSFUL …
sidings\…\6B6EACC355EC212F     4707 B → 7442 B   +2735 B
  增量来自 sidings 里多了一条 vehicle 记录（重建出来的那台车），不是路径缓存
```

结论可以收窄了：**没有「路径缓存」被写进磁盘**。桥调 writePathCache 之后，落盘的只有
`lastGeneratedMillis` 这个时间戳。既然路径本来就不落盘、开机由宿主重算，
那么「宿主不采用缓存」这个说法可以放下了——不是不采用，是根本没有可采用的缓存。

这也解释了为什么 persistPath 无论怎么修都不会让 v1.7 的丢失消失；
`audit + 重建` 这条替代路线是对的。

### events.seq

每条事件带 seq，会话内 1,2,3… 单调（实测：1 deploy_train / 2 set_platform / 3 deploy_train）。
**跨重启归零**（每个 boot 都从 1 开始），所以增量拉取要按 (boot, seq) 或按 `at` 去重。
建议在 `/health` 里加 `sessionStartedAt` 或 `bootId`。

## 7. 新发现（按优先级）

### P1 ① · 配置带 UTF-8 BOM → 静默回落默认值（token 失效 + 开关失效）

证据链：

```text
文件首字节：EF BB BF 7B 0A 20 22      ← Windows 记事本 / PowerShell 5.1 默认写出 BOM
启动日志：dispatch bridge loaded (127.0.0.1:8889, token disabled, dryRun false)
          ← 文件里写的是 token: testtoken
事件原文：path generation produced nothing; depot regeneration is disabled
          (allowDepotRegeneration=false); previous path restored
          ← 文件里写的是 allowDepotRegeneration: true
```

`BridgeConfig.load()` 里 `Json.parse` 遇到 BOM 抛异常，被 `catch` 吞掉后返回**全默认配置**：
token 变空、`allowDepotRegeneration` 变 false。运维只会看到「开关没生效」，
而 token 变空是安全面的问题（当前靠 `bindAddress` 是 loopback 兜住）。

建议：

```java
String text = Files.readString(path, UTF_8);
if (!text.isEmpty() && text.charAt(0) == '\uFEFF') text = text.substring(1);
// 解析失败不要再静默：记录异常并在 /health 暴露 configError
```

顺带：`/health` 完全没有回显实际生效的配置（port/token 是否启用/两个开关），
建议加一个 `settings` 小节，让「文件写了什么」和「进程用了什么」能一眼对比。

### P1 ② · pathRecoveryNeeded 逐维度覆盖（见 §3）

改成累加：一次巡检把所有维度收集完，再一次性写入；或按维度 id 分组返回。

### P1 ③ · audit / recover 只取 simulator(0)

```java
final Simulator simulator = host.simulator(0);   // BridgeCommands.audit / recover
```

而维度顺序在同一份存档的不同 boot 之间会变。本轮实测到的顺序：

```text
boot1  overworld, the_nether, the_end
boot2  overworld, the_end, the_nether
boot6  overworld, the_end, the_nether
boot9  overworld, the_nether, the_end
```

这次 overworld 恰好一直是 0，所以命令没出错；但只要它排到 1 或 2，
`/mtbridge audit` 会对一个没有车厂的维度体检并回答 `all depots have paths`（假阴性），
`/mtbridge recover` 则什么都不做还回 `recovered 0 depot(s)`。
tick 里的自动巡检已经遍历了所有维度，命令侧应该保持一致。

### P2 ④ · 恢复动作不可观测（见 §4）

建议：`recover` / `autoRecover` 成功后 `fire(...)` 一条事件，并写：

```json
"lastRecovery": { "depot": "2（线路中）", "depotId": "64542daa4ef67d13",
                  "sidings": 2, "trains": 2, "mode": "manual|auto", "at": 1792688559000 }
```

### P2 ⑤ · 服务侧 `bridge.mode: observe` 会把桥整体关掉

实测：observe 模式下 `bridge.configured=false`，于是没有车辆身份，
兼容性降级为 `DEGRADED missing=[vehicle_identity, platforms]`，「只出 advisory」也出不了有用的。
建议加 `bridge.mode: telemetry`（读 `/state`、绝不 POST `/command`），
`actuator.mode: dry-run` 已经能做「算但不发」，两个配一起正好是只读联调形态。

### P2 ⑥ · audit 输出格式

`parkedTrains` 实际是**车厂内所有车辆数**（含路径正常那条侧线的车），本轮出现过 `parkedTrains=2`
但真正丢路径的只有 1 条侧线 1 台车的情况。语义没错（§3.1 伪代码就是 `sum(vehicles(siding))`），
但名字容易被读成「受影响的列车数」；建议改名 `depotVehicles`，另给 `lostSidings` 的计数。

## 9. 建议的下一步

1. 修 P1 ①②③（都是十几行以内的改动，但决定了运维能不能用、命令会不会打错车厂）；
2. 若继续真机专项，建议只测两件：
   - 维度顺序被打乱时（例如让 overworld 排到 index 2），audit/recover 是否仍打对车厂；
   - 「重生成过程中停机」→ 重启 → 自动/手动恢复的完整闭环（本轮已能稳定复现，配方见 §2）。

**一句话：v1.8 的三项功能（体检、手动恢复、自动恢复）在真机上全部达标，恢复结果还能活过重启；
但对外 advisory 字段是空的、命令侧只认维度 0、配置带 BOM 会静默失效——这三处不修，功能对运维基本等于不可见。**
