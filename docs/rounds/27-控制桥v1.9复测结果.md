## 1. §8.1：带 BOM 的配置（两次对照）

配置文件**故意写成 UTF-8 BOM**（这正是上一轮静默失效的那种文件）：

```text
首字节  EF BB BF 7B 0A 20
```

### 第一次（allowDepotRegeneration=false）

```json
{ "enabled": true, "port": 8889, "bindAddress": "127.0.0.1", "token": "***",
  "maxHoldSeconds": 600, "intentTtlSeconds": 120, "dryRun": false,
  "allowDepotRegeneration": false, "httpThreads": 8, "configError": "" }
```

token 回显成 `***` 就说明解析成功了（默认配置下这里是空串），`configError` 为空。
顺带确认 token 真的在拦截：

```text
无 Authorization       → 401
Authorization: wrong   → 401
Authorization: correct  → 200
```

### 第二次：换成非默认数值，证明是逐键读进来的

文件里写 `maxHoldSeconds: 321`、`intentTtlSeconds: 77`、`httpThreads: 4`，
`/health.settings` 原样回显：

```json
{"enabled":true,"port":8889,"bindAddress":"127.0.0.1","token":"***",
 "maxHoldSeconds":321,"intentTtlSeconds":77,"dryRun":false,
 "allowDepotRegeneration":false,"httpThreads":4,"configError":""}
```

### 第三次：BOM + `allowDepotRegeneration: true`，验证开关**有行为**而不只是回显

```json
… "allowDepotRegeneration": true …"configError":""
```

这次开机后自动修复真的触发了（见 §4），说明开关既被读进来、也真的放行了策略 2。
上一轮「文件写 true、进程按 false 跑」的问题不复现。

## 2. §8.1b：坏 JSON 不再静默

把配置写成截断的 JSON 再启动：

```text
config/mtbridge.json = "{ \"enabled\": true, \"token\": \"testtoken\", ,, broken"

/health.settings = {
  "token": "",
  "maxHoldSeconds": 600,
  "allowDepotRegeneration": false,
  "configError": "config unreadable, using defaults: expected string at 41"
}
```

`configError` 带上了解析位置（`at 41`），比上一轮的纯静默强得多；桥仍然正常监听（fail-open 只在 loopback，
非 loopback + 无 token 依旧拒绝启动）。

## 3. §8.2：advisory 不再被下一个维度冲掉

制造一条丢路径的侧线（复现配方见 §5），重启后每 3 s 采样 27 s：

```text
t+0s   pathRecoveryNeeded=[]                                    ← 首个巡检周期未到
t+3s   []
t+6s   []
t+9s   []
t+12s  [{"depot":"2（线路中）","depotId":"64542daa4ef67d13",
         "sidings":["a37272e024f03a0c"],"lostSidings":1,"depotVehicles":2}]
t+15s  同上
…
t+27s  同上                                                      ← 一直保留
```

本 boot 的维度顺序是 `overworld, the_end, the_nether`——**最后一维（下界）没有车厂**，
这正是 v1.8 里把字段冲成空的场景。现在稳定保留。

两点说明：

- 开机后前约 10 s 为空是正常的（首个 200 tick 巡检周期还没跑），不是回归；
- 字段与 `/mtbridge audit` 输出逐字一致，两个入口不再互相打架。

## 4. §8.3 / §8.4：命令跨维度 + 恢复可观测

### 手动（`/mtbridge recover`）

```text
/mtbridge audit   → [{depot=2（线路中）, depotId=64542daa4ef67d13,
                      sidings=[a37272e024f03a0c], lostSidings=1, depotVehicles=2}]
/mtbridge recover → recovered 1 depot(s)

/health.lastRecovery = {"depot":"2（线路中）","depotId":"64542daa4ef67d13",
                       "sidings":1,"trains":2,"mode":"manual","at":1792689579919}
/health.events[0]    = seq=1 kind=recover_depot outcome=APPLIED
                       target=64542daa4ef67d13
                       message="recovered depot 2（线路中） (manual)"
```

恢复后：`pathRecoveryNeeded=[]`、`audit → all depots have paths`、两条侧线 planned 恢复，
车厂 2 的两台车都换了 id，车厂 1 的两台车 id 未变。

### 自动（开关打开后重启）

```text
t+0s … t+8s   lost=[a37272]              lastRecovery={}
t+10s         lost=[]                    lastRecovery={"depot":"2（线路中）",
               "depotId":"64542daa4ef67d13","sidings":1,"trains":2,"mode":"auto",…}

events[0] = seq=1 kind=recover_depot outcome=APPLIED :: recovered depot 2（线路中） (auto)
lastError = "auto-recovered depot 2（线路中） (paths were missing)"
```

服务端日志同步带上了新字段：

```text
depots with missing paths: [{depot=2（线路中）, depotId=64542daa4ef67d13,
  sidings=[a37272e024f03a0c], lostSidings=1, depotVehicles=2}]
  (auto-recovered 1, allowDepotRegeneration=true)
```

`mode: manual|auto` 区分正确，事件 target 是 depotId，seq 与普通命令事件共用同一个计数器。

### 关于「维度顺序错位」这条复测项

本轮 4 次启动实测到的顺序：

```text
boot1  overworld, the_end,    the_nether
boot2  overworld, the_end,    the_nether
boot3  overworld, the_nether, the_end
boot4  overworld, the_nether, the_end
```

overworld 四次都排在 index 0，**没法在本环境里人为把它挤到 1 或 2**，所以「overworld 不在 0」这条
无法直接实测。可替代的等价证据有两条：

1. 命令侧代码已按 `0..dimensionCount-1` 遍历并合并（`simulators(host)`），不再是 `simulator(0)`；
2. 「最后一维为空」这个当年造成假阴性/字段清空的条件，本轮每次都成立，且 audit 与 advisory 都正确。

结论按「实现验证 + 等价条件验证」记通过，并把「把 overworld 挤到 index 2」留作下一轮的真实环境专项。

## 6. 遗留（P2）

### ① 自动修复后 advisory 残留一个巡检周期

巡检顺序是 `auditAll → 发布 → autoRecover`，修复完成后没有重新发布，所以：

```text
t+10s  lastRecovery.mode=auto、lost=[]，但 pathRecoveryNeeded 仍非空
t+20s  下一个周期才变成 []
```

建议：`autoRecover(...) > 0` 之后补一次 `service.auditAll(simulators)`（或直接把空表发布出去）。
影响有限（≤1 个周期，且 lastRecovery 已给出准确时间点），但外部若据此做告警会多响一声。

### ② configError 只活在 /health 里

坏配置启动时，服务端日志只有：

```text
[mtbridge/]: dispatch bridge loaded (127.0.0.1:8889, token disabled, dryRun false)
```

——**没有一句提到配置解析失败**。运维只看控制台的话，会以为「就是没配 token」。
建议构造函数里 `if (!config.configError.isEmpty()) LOGGER.error("bridge config error: {}", config.configError);`。

### ③ 两处小瑕疵（不影响行为）

```java
// BridgeService.recordRecovery：两个分支相同，三元表达式是多余的
fireRaw(mode.equals("auto") ? Source.COMMAND : Source.COMMAND, …)

// 全量重建分支（onlyBroken=false）里 sidings 取 savedRails.size()、trains=0，数据不准
recordRecovery(depot, Map.of(), "manual");
```

全量重建目前没有调用者（命令与巡检都只传 onlyBroken=true），属预防性提示。

### ④ audit 的文本输出仍是 Java map 的 toString

```text
[{depot=2（线路中）, depotId=64542daa4ef67d13, sidings=[a37272e024f03a0c], …}]
```

人读没问题，机器解析请走 `/health.pathRecoveryNeeded`（那里是标准 JSON）。
若希望命令输出也能被解析，可以改成 JSON 字符串。
