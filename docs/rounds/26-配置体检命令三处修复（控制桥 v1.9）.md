# 26 · 配置/体检/命令三处 P1 修复（控制桥 v1.9）

对应报告：25-控制桥v1.8复测结果.md

产物：mtbridge/build/libs/mtbridge-1.9.0+1.20.1.jar（93,320 字节，reobf）
服务侧无改动。

---

## 1. 报告结论的确认

v1.8 的三项功能（体检、手动恢复、自动恢复）在真机上全部达标，恢复结果能活过重启。
报告还把“persistPath 无效”解释清楚了：**宿主根本不把路径写进存档**（SHA1 比对显示
depot 文件只差 3 个字节 lastGeneratedMillis，siding 文件增量是新增车辆记录），
路径是开机重算的。所以 persistPath 不再是恢复手段，这条判断我接受。

本轮只修报告新发现的三个 P1（都决定运维能不能用），外加两个 P2。

---

## 2. P1①：配置带 BOM 导致静默回落默认值

**根因**：Windows 编辑器写入 UTF-8 BOM，Json.parse 抛异常，catch 后返回**全默认**——
token 变空、allowDepotRegeneration 变 false，运维只看到“开关没生效”。

**修复**：

1. 读文件后剥离 BOM（charAt(0) == 0xFEFF 则 substring(1)）；
2. 解析失败不再静默：configError 记录下来；
3. /health.settings 回显**进程实际生效**的配置（含 configError），与文件内容一眼可比。

对应的安全面影响：token 失效此前只靠 loopback 兜住，现在配置错会直接可见。

---

## 3. P1②：pathRecoveryNeeded 被逐维度覆盖

**根因**：MtBridgeMod 按维度循环调用 service.auditDepots(simulator)，而该方法每次用本维度结果
整体覆盖共享字段；最后一维（下界）没有车厂 → 返回空表 → 覆盖成空。

**修复**：新增 service.auditAll(List<Simulator>)：一次巡检所有维度、合并、只发布一次。
内部拆出 collectBroken(simulator)（不写字段），auditDepots 保留单维度语义供内部使用。

---

## 4. P1③：audit / recover 只取 simulator(0)

**根因**：命令侧写死 host.simulator(0)，而维度顺序在不同 boot 之间会变
（报告实测 boot1/boot2 顺序相反）。overworld 排到 1 或 2 时，audit 会对空维度回答
“all depots have paths”（假阴性），recover 则空转。

**修复**：命令侧改为遍历全部维度（与 tick 巡检一致），recover 用
service.recoverDepots(List<Simulator>, onlyBroken)，audit 用 auditAll。

---

## 5. P2④：恢复动作可观测

recover / autoRecover 成功后：

- 写 /health.lastRecovery：{ depot, depotId, sidings, trains, mode: manual|auto, at }
- 发一条事件（events 里 kind=recover_depot，seq 递增）
- lastError 仍然保留自动恢复的说明

事件走的是新的 fireRaw()（不依赖 BridgeCommand），监听器同样会收到 BridgeEvent。

---

## 6. P2⑥ 与事件序号

- audit 输出字段改名：parkedTrains → depotVehicles（车厂内车辆数），并新增 lostSidings（受影响侧线数），
  避免被读成“受影响列车数”；
- /health 增加 bootId 与 sessionStartedAt：events.seq 跨重启归零，调用方可用 (bootId, seq) 做增量。

## 7. 未做

P2⑤（服务侧 bridge.mode: observe 会把桥整体关掉，建议增加 telemetry 只读模式）属于服务侧改动，
本轮未做。建议的改法：新增 mode=telemetry，只把桥当遥测源、绝不 POST /command，

## 8. 复测建议

1. 用带 BOM 的 config/mtbridge.json 启动：token 与 allowDepotRegeneration 应生效，
   /health.settings 里能看到实际值与 configError（正常时为空）；
2. 制造一条丢路径的侧线：/health.pathRecoveryNeeded 应稳定列出该车厂（不再被下一个维度冲掉）；
3. 打乱维度顺序（或直接看 boot 日志）：/mtbridge audit 与 recover 仍应打对车厂；
4. 执行 /mtbridge recover：/health.lastRecovery 与 events（recover_depot）都应有记录。
