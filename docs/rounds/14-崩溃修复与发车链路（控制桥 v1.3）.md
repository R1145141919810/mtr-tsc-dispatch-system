## 1. P0 · dwell_control 打死服务器

### 1.1 根因

VehicleSchema.elapsedDwellTime 是 long，桥用 Field.setDouble 去写，JDK 抛 IllegalArgumentException，
Reflect.setDouble 把它包成 IllegalStateException，BridgeService.tick 的 dwellHolds.forEach 没有捕获，
异常穿出 onServerTick → Forge 判定 tick 崩溃。

### 1.2 修复：按字段真实类型读写

    public static void setNumber(Object target, String name, double value) {
        Field field = field(target.getClass(), name);
        Class<?> type = field.getType();
        if (type == long.class)       field.setLong(target, (long) value);
        else if (type == int.class)   field.setInt(target, (int) value);
        else if (type == float.class) field.setFloat(target, (float) value);
        else                          field.setDouble(target, value);
    }

写入、读取（dwellElapsed 之前恒为 0 就是同类问题）全部改走 getNumber/setNumber，
setDouble/getDouble 不再被试用于未知类型的字段。

### 1.3 三层防线（不只修那一行）

| 层 | 行为 |
|---|---|
| 字段层 | 类型自适应读写，不再有“double 写 long”这种必然异常 |
| tick 层 | tick() → tickInternal() 整体 try/catch；单个持有项再单独 try/catch，异常移除该持有并 tickFailures+1 |
| 宿主层 | MtBridgeMod.onServerTick 外层 try/catch，任何桥异常只记 ERROR 日志，绝不冒泡到服务器 tick |

新增 /dispatch/v1/health.tickFailures，tick 内被吞掉的异常次数可见；lastError 记录最后一条。

## 2. P1 · 重生成后列车无法发车

### 2.1 根因

旧实现把 departureIndex 钳到 0 再 startUp：

    long departureIndex = Math.max(0L, Reflect.getLong(vehicle, "departureIndex"));

但 departures 里根本没有 0 号班次，宿主在 simulateVehicles 里按
「departureIndex >= departures.size() → 移除」处理，于是车被删除、重新生成、永远停场。
startUp 不抛异常，所以症状是“看起来成功、车不动”。

### 2.2 修复：不造索引，按三种真实情况走

    long scheduled = Reflect.getLong(vehicle, "departureIndex");
    if (scheduled >= 0) { startUp(scheduled, now); return applied; }        // ① 有班次：提前发车
    if (siding.addDeparture(now)) return deferred("host dispatches next tick");  // ② 无班次：向侧线要一个
    if (!added && siding.area != null) {
        siding.area.generatePlatformDirectionsAndWriteDeparturesToSidings(); // ③ 时间表被清空 → 重建
        added = siding.addDeparture(now);
    }
    if (siding.getIsManual()) return rejected("siding is manual");           // ④ 手动侧线：明确拒绝
    return failed("siding refused a departure slot (no timetable segments)"); // ⑤ 其他：明确失败

关键点：索引只来自真实班次，绝不臆造。②/③ 走宿主自己的发车簿，由它在下一 tick 调度，
而不是桥去 startUp 一个不存在的班次。

### 2.3 发车意图改为等“路径就绪”

侧线意图原先固定等 1 s。现在等 pathSidingToMainRoute 非空（重建后的路径真正生成）再发车，
deadline 内没就绪则 failed "path regeneration never settled"，不会挂着直到超时静默。

### 2.4 需要复测确认的点

本地无法验证宿主是否接受 addDeparture(now)。若仍不驶出，下一步杠杆是
Depot.generateDepots(Simulator, ObjectArrayList<Depot>)——车厂级生成会重新分配 departureIndex，
但会清空该车厂所有车，因此没有默认启用，建议作为 allowDepotRegeneration 开关由运维显式打开。

## 3. P1 · since 永远 304 不了

版本号原来是 simulator.getCurrentMillis()——随时钟走，version <= since 永不成立。

现在改为内容版本：对去掉时间字段后的 payload 做 FNV-1a，只有内容变化才 revision+1。

    state?since=17  → 200 (version=18)   首次
    state?since=18  → 304                内容没变
    state?since=18  → 200 (version=19)   有车动了

ETag 同步改用 "v<revision>"。

## 5. P2 · 维度顺序不稳定

同一存档两次启动，宿主给出 overworld/the_nether/the_end 与 overworld/the_end/the_nether 两种顺序。
用 index 钉维度必然每次重启都可能报错。

服务侧改为按 id 重映射：

    配置 index=2 id=minecraft/the_nether，桥报告 [overworld, the_end, the_nether]
    → 按 id 找到 index=1 → 运行时改写为 1，WARN 日志 + validation 一条 WARN
    → 只有“id 完全不存在”才是 ERROR（强制桥模式仍 exit 2）

桥侧仍以宿主顺序为准（?dimension= 的真实语义不能伪造），稳定化由调用方按 id 做。
