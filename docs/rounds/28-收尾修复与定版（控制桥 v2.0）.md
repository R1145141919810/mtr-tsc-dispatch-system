## 2. 仍开放（服务侧）

P2⑤：bridge.mode 增加 telemetry 只读模式。建议三处改动（服务侧，下一轮可做）：

1. Config.bridgeEnabled()：把 telemetry 与 auto/bridge 一并视为启用；
2. Service.resolveChannels()：telemetry 模式下只创建 BridgeSource 作为遥测源，
   不创建 BridgeActuator（写通道留给 rcon/dry-run）；
3. DimensionRuntime 的 preferBridge：改用“桥可用（probe 成功）”而不是“桥执行器在线”，
   否则 actuator 为空时遥测也会退回原版 HTTP。

配合 actuator.mode=dry-run 就是完整的“只读联调”形态。

## 4. 从 v1.0 到 v2.0 的关键结论（供后续维护参考）

1. 列车路径在班次内不可变；改台只能重建路径，而重建是**清空 + 异步生成**。
2. generateRoute(platform, null, -1) 在该线网产不出路径；策略 1 (platform, platform, 0) 可以。
   所以“多策略 + 超时升级”不是冗余设计，是必需。
3. 路径重建后车辆会被重建（新 id），任何按旧 id 的排队动作都必须改为按侧线。
4. 路径就绪的**同一 tick** 发车会被宿主丢弃；延迟约 1.5 s 后发车 100% 成功。
5. 发车必须做后置校验（下一 tick 查车是否存在 / 是否在线上），否则会出现假 APPLIED。
6. 宿主不把路径写进存档（重启重算），因此“持久化路径”不可行，
   正确策略是“检测 + 车厂级重建”。
7. 维度顺序每次 boot 可能不同，任何按 index 的假设都必须遍历全部维度或按 id 匹配。
8. 配置解析必须显式报错（BOM/坏 JSON 曾导致 token 与开关静默失效）。

## 5. 定版说明

v2.0.0 功能冻结：选台、发车、回场、压站四条指令链路均已在真机闭环，
恢复能力（audit / recover / 自动恢复）与可观测性（events / lastPersist / lastRecovery /
pathRecoveryNeeded / settings）齐备。

后续只建议做两类维护：

- 宿主升级（MTR/TSC 新版本）后的字段/方法兼容性回归：重点看 Reflect 的字段名、
  Siding.generateRoute 的语义、VehicleSchema 的字段类型；
- 服务侧 telemetry 只读模式（§2），属独立改动，不影响桥的接口。
