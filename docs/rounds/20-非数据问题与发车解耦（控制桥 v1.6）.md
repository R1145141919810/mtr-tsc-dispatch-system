## 1. 先回答你的问题：4b 不是线网数据问题

报告 [4b] 的现象是“带目标 deploy 后路径正确、车不发”。判断依据：

| 证据 | 说明 |
|---|---|
| 同一条侧线、同一辆车，普通 deploy 1 s 内 onRoute=true 且速度爬升 | 侧线与车辆本身完全可发车 |
| 4b 里 planned 已等于目标台（9a0cfd），routeDiag 已清空 | 路径生成成功，不是“建不出来” |
| health: exec=4 failed=0 pendingIntents=0，lastError 空 | 排队的发车意图既没执行也没报错 |

如果真是线网数据问题，表现会是 [2b] 那样：策略升级、failed、回滚、planned 回到旧值。
而 4b 的 planned 是新目标台、路径就绪，只是那辆车没被发出去。

真正属于线网数据的只有你构造的 [2b]（线路2侧线 → 线路1平台），桥已正确判定不可达并回滚，
那条不需要改代码，属于“目标选错”。

### 根因

带目标 deploy 会排一个“侧线意图”，它由 tick 里的意图循环解析侧线：

    Siding target = simulator.sidingIdMap.get(intent.sidingId());   // 旧代码

上一轮我已把路由尝试的同类查找改成线性扫描，但**漏改了意图循环**。
于是意图拿不到侧线 → vehicle 为 null → 到 deadline 静默移除（pendingIntents 归零、failed 不涨），
与 4b 的观测完全一致。

## 2. 本轮改动

### 2.1 意图循环改用同一个查找（桥）

    Siding target = findSiding(simulator, intent.sidingId());   // 线性按 id

### 2.2 发车与“路径就绪”解耦（桥）

过去：路径好了以后等下一次 tick 的意图循环来发车（而那个循环有上面的 bug）。
现在：**路径就绪的那一刻，直接完成排队中的发车**，并对当前车辆实例执行：

    if (routeSegments(siding) > 0) {
        persistPath(siding);
        fire(applied "path ready via 策略N");
        completePendingDeparture(simulator, siding, now);   // 取出 siding:<id> 意图 → depart → fire
    }

失败时同样立即收尾：

    failPendingDeparture(intentFor(siding), reason, now);   // 路径失败 → 排队发车立刻 failed，不再干等 15 s

### 2.3 路径落盘（报告 §2）

成功生成路径后调用宿主的 writePathCache()（包私有，反射调用，且**只在路径非空时**调用，
所以不会把“重建窗口中的空路径”写进存档）。

这是对“重生成 → 存档 → 重启丢路径”的直接缓解；已损坏的存档仍需一次车厂重建。

### 2.4 服务侧把 pathLost 当硬阻断（报告 §3）

- 解析 vehicles[].pathLost；
- 选台、绕行、回场三类决策循环都跳过 pathLost=true 的车；
- 计数 dispatch_skipped_total{reason=path_lost}，不再对“根本发不出去的车”产生决策。

## 3. 复测（只需一件事）

    deploy_train(car, platform) → 期望：3 s 内 onRoute=true，而不是停在 deferred

判断口径：
- 若发车成功：routeDiag 在路径就绪时消失、exec+1、车动；
- 若仍失败：现在一定会有 failed 事件或 lastTickError（不再静默），把那条原文发我。

其余链路（普通 deploy、dwell、策略升级、回滚）本轮未触碰，应无回归。

## 4. 仍未解决 / 风险

1. writePathCache 是宿主包私有方法，反射调用；宿主升级改名会静默失效（persistPath 返回 false，目前未上报，
   可作为下一轮的观测项）。
2. 策略 2（车厂级重建）仍默认关闭：破坏性不变。
3. 若目标平台与该侧线物理不连通，桥会升级→失败→回滚，这是正确行为；调用方应改用可达站台。
