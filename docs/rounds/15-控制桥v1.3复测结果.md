## 1. 逐项结果

### [1] `dwell_control` 30 s — ✅ 通过

```text
POST {"kind":"dwell_control","vehicleId":"-86837…","args":{"seconds":30}}
→ { "outcome":"applied", "message":"dwell hold set" }
health: tickFailures=0, holds=[{vehicle:-86837…, remainingSeconds:27}]
30 s 后: holds=[], tickFailures=0, 无崩溃报告
```

### [2] `dwell_control` −1（封顶 600 s）— ✅ 通过

```text
→ { "outcome":"applied", "message":"dwell hold capped to 600s" }
holds=[{vehicle:804277…, releaseAt:+597s}]
10 分钟后: autoReleased=1, holds=[], tickFailures=1, 无崩溃报告
```

唯一的杂音是 `tickFailures=1`：有异常被吞掉了，但 **`lastError` 为空、服务器日志里也没有对应 ERROR 行**，
拿不到任何线索。建议：吞异常时至少把类型+字段名写进 `lastError`，并每个不同消息只打一条 WARN，
否则 `tickFailures` 只是个无法定位的计数器。

### [3] 停场车 `deploy_train`（无目标）— ❌ 失败（回归）

```text
deploy_train(859109…) → deferred "departure queued"
t+1s…t+5s: onRoute=False speed=0.0 pathReady=False next=000000
health: failed=0, deferred=2, intents=[]
```

上一轮（v1.2）这一步 2 s 内就走了。v1.3 把“钳 departureIndex 再 startUp”换成
`siding.addDeparture(now)` 之后，**这条路彻底不动了**，而且不报错——`failed` 计数仍是 0。

### [4] `deploy_train(train, platform)` — ❌ 失败

```text
before: planned='4ad4105fad8390aa'（站点1/1）  pathReady=False
deploy_train(859109…, 430a53) → deferred "path regenerated; departure queued on siding 9d16…"
t+2s: id=888606…（重建成功） planned='0' pathReady=False run=False
t+12s: 同上
pendingIntents=[{ vehicle:"siding:-7127443172031826443", kind:deploy_train,
                  target:430a53…, deadline:+15s }]
```

侧线意图一直等到 deadline（等 `pathSidingToMainRoute` 非空），而路径始终没生成。

### [5] `set_platform` 停场车换台 — ❌ 失败（但把根因暴露了）

```text
before: planned='4ad4105fad8390aa'   ← 正常停场车有计划首站台
set_platform(…, 430A53) → deferred（不再被拒，✓ 上一轮的 P1 判定修复有效）
after : id=764046…（重建） planned='0'  pathReady=False
```

**`plannedFirstPlatformId` 从有效值变成 `"0"`**，说明 `generateRoute` 之后侧线路径是空的。

对照 MTR 4.0.5 的方法签名：

```text
javap org.mtr.core.data.Siding
  public void generateRoute(Platform, Platform, int, long);
  public boolean addDeparture(long);
```

桥目前调用 `generateRoute(platform, null, -1, altitude)`。两个 Platform 参数 + 一个 int，
传 `null` 与 `-1` 很可能就是“生成不出路径”的直接原因。建议按下列顺序试，每次只用真机验证一条：

1. `generateRoute(target, target, 0, altitude)`（不传 null、索引给 0）；
2. 若仍空，改用 `Depot.generateDepots(simulator, [depot])`（你文档里的 `allowDepotRegeneration` 开关），
   它本来就会重建整条车厂的 departureIndex；
3. 无论哪条，**都要在 `state` 里回填 `pathReady/plannedFirstPlatformId` 后再宣称 `deferred` 成功**，
   现在“接受但永不生效”的状态最难排查。

### [6] `state?since` — ✅ 通过

```text
version=18 → since=18 → 200（这 1 s 内有车状态变化，版本已到 19）
version=20 → since=20 → 304
ETag: "v20"
```

内容版本生效了。注意：**有车在动时几乎每次都会 200**（`dwellElapsed` 等每 tick 变），
只有在全停场时才稳定拿到 304。这符合“内容版本”的定义，不是缺陷，但别指望它省多少带宽。

### [7] 维度按 id 重映射 — ⚠️ 先发现服务侧 bug，修复后通过

第一次运行（用户交付的 223,436 B 版本）日志自相矛盾：

```text
WARN dimension index remapped by id id=minecraft/the_nether configured=1 actual=2
INFO dimension runtime ready dimension=minecraft/the_nether index=1      ← 用的还是旧索引
```

原因在我这边：`Service.start()` 在调用 `resolveChannels()`（内部做重映射）**之前**就把
`enabledDimensions()` 存进了局部变量，重映射只改了 `config`，运行期仍用旧列表。

修复后（本轮重新构建，78/78 自检仍全绿）：

```text
WARN dimension index remapped by id id=minecraft/the_nether configured=1 actual=2
INFO dimension runtime ready dimension=minecraft/overworld index=0
INFO dimension runtime ready dimension=minecraft/the_nether  index=2
/v1/status: dimensions=minecraft/overworld@0, minecraft/the_nether@2  validation.ok=true warnings=2
```

不再 exit 2、不再连错维度。

## 2. 需要重点回传的两条

### 2.1 重生成产出空路径（P1 根因，比 departureIndex 更靠前）

证据：`plannedFirstPlatformId` 从 `4ad4105fad8390aa` 变为 `"0"`，`pathReady` 恒 false。
推论：不是“发车时机”问题，而是 **`generateRoute` 根本没生成路径**；
所以 §2.2 里那套 departureIndex 分支（addDeparture / 车厂重建）在当前路径下根本没机会执行。
建议先修“让路径真的生成”，再看发车。

### 2.2 普通发车（无目标）在 v1.3 回归

v1.2 能走（虽然是靠错误的 departureIndex=0），v1.3 改成 `addDeparture` 后完全不动且不报错。
两种可能：`addDeparture(now)` 返回 true 但宿主不在下一 tick 调度；或返回 false 后走了你的
“时间表被清空 → 重建”分支但那个调用也没生效。
建议在 `BridgeResult` 里把 `added` 的真实值与分支走向写进 `detail`，否则外部只能看到 “departure queued”。

## 4. 建议的处理顺序

1. **先让路径生成**（`generateRoute` 参数或 `Depot.generateDepots` 开关），用
   `plannedFirstPlatformId` 是否非 `"0"` 作为唯一验收条件——这比“车有没有动”更快定位。
2. 路径就绪后再修发车（§2.2），验收用 `onRoute=true` + `pathReady=true`。
3. `tickFailures` 补 `lastTickError` 与一次性日志。
4. 大规模压测与“两辆停场车”场景仍待补（本轮不阻塞）。

**结论：P0 已清零，可以放心用 `dwell_control`；P1 仍卡在“重生成产不出路径”，
在它修好之前，选台/绕行/回场这三条依赖路径重建的链路都无法真机闭环。**
