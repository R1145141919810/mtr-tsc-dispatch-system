# 22 · 假成功修复与发车校验（控制桥 v1.7）

对应报告：21-控制桥v1.6复测结果.md

产物：mtbridge/build/libs/mtbridge-1.7.0+1.20.1.jar（88,416 字节，reobf）
服务侧本轮无改动（223,572 B）。

---

## 1. 判定

不是线网数据问题，是**时序 + 假成功**两件事：

- 证据链：同一侧线、同一辆车，普通 deploy 1 s 内 onRoute=true；带目标的那次在“路径就绪的同一 tick”
  立刻 startUp，车被宿主删除，随后 MTR 补了一辆停场车。
- depart() 只判断 startUp 有没有抛异常，所以对外报了 applied（exec+1），而车其实已经不存在。

结论：发车实现本身没坏，是**调用时机**和**成功判据**两个问题。

---

## 2. 修复 A：路径就绪后不再立刻发车

    notBefore = pathReadyAt + 1500ms        // 与“普通 deploy 成功”的时序对齐
    if (now < notBefore) { 保留意图，下一 tick 再来 }

路径就绪的那次 tick 只更新时间戳，真正 depart 放到 1.5 s 后。
这也是报告 §P0 第二条的建议（1–2 s）。

---

## 3. 修复 B：发车后置校验（不再假成功）

depart 之后不再直接 fire(applied)，而是登记一条待校验记录：

    verifications[vehicleId] = { departAt: now, deadline: now + 6s }

之后每 tick 校验：

    车不存在                  → failed "departed vehicle was dropped by the host (startUp did not stick)"
    存在但 !getIsOnRoute 且超时 → failed "departure did not take effect within 6000ms"
    存在且 getIsOnRoute       → applied "departed and verified on route"
    存在但还没上线（<6s）      → 继续等

首检在 depart 后 600 ms 开始，既给宿主一两个 tick，又不至于长时间悬空。
失败会同时写 lastError 与 tick 错误（去重 WARN），并在事件里留原文。

---

## 4. 修复 C：persistPath 的结果可见（报告 §P1）

- /health.lastPersist：{ siding, ok, at, method }
- /health.persistFailures 计数
- ok=false 时同时写 lastError 与一条去重 WARN
- 路径就绪事件的文案区分 “persisted” / “NOT persisted”

这样下次重启后路径再丢，就能直接判断是“反射没命中”还是“写盘成功但宿主不认”。

---

## 5. 修复 D：事件回放（报告 §P1）

/health.events 保留最近 20 条：

    { at, kind, target, outcome, message }

21 号报告里“唯一拿不到的关键信息是 applied 事件原文”，这条补上后同类问题不需要再猜。

---

## 6. 复测口径

    部署带目标:
      t+0      deferred "path regenerated; departure queued on siding <id>"
      t+~3s    applied "path ready via 策略0, persisted"（若 persist 失败会写 NOT persisted）
      t+~4.5s  开始 depart，进入校验
      t+~5s    applied "departed and verified on route"    ← 目标结果
      或        failed "…dropped by the host…" / "did not take effect…"

    普通 deploy: 应仍 1 s 内 onRoute（未改动那条路径）
    dwell_control: 应仍不崩

如果这次仍然发不出去，/health.events 与 /health.lastError 会直接给出原因，
不需要再看 telemetry 猜。
