## 1. ① 未达成：刷新跑在重建完成之前

### 实测（自动恢复，400 ms 采样）

```text
t+0.0s   need=0   lastRecovery=-
t+8.8s   need=1   lastRecovery.mode=auto (at=1792690348924)   ← 修复已发生
t+9.2s   need=1   ← 之后每个采样点都是 1
…
t+17.6s  need=1   ← 距修复已 8.8 s，advisory 仍是“需要恢复”
```

这一轮 23 个采样点里有 23 个是「lastRecovery 已置位、pathRecoveryNeeded 仍非空」，
也就是 v2.0 想消除的那种不一致**依然存在**。

### 实测（手动恢复，300–1000 ms 采样）

```text
t+0.0s  /mtbridge recover → recovered 1 depot(s)
        紧接着读：pathRecoveryNeeded 仍是那条 broken 记录
t+5.0s  need=1   audit=仍报 broken   车厂内车辆已换成新 id（lost=false）
t+7.9s  need=0   audit=仍报 broken   ← 重建期间车厂在健康/不健康之间抖动
约 t+10s 之后稳定：need=0、audit=all depots have paths
```

### 原因

`Depot.generateDepots(...)` 是**异步**的：策略 2 实测要 ~6 s 才产出路径（v1.9 报告 §2 的时间线：
t+0.8 发起 → t+6.1 才 `path ready`），期间 `routeSegments(siding)` 一直是 0。

v2.0 的补丁是同步的：

```java
final int recovered = service.autoRecover(simulators);
if (recovered > 0) {
    service.auditAll(simulators);   // ← 此刻路径还没生成，重新发布的还是 broken
}
```

所以这次刷新只是**把同样的结果又发布了一遍**，一个周期后的巡检才是真正生效的那次。
手动恢复路径（`recoverDepots` → `auditAll` 取目标 → 重建）有同样的问题，且完全没有刷新调用。

### 三个改法（按改动量从小到大）

1. **延后刷新**：恢复成功后置 `pendingAdvisoryRefresh`，在后续 tick 里（例如受影响车厂
   `routeSegments > 0`，或最多 N tick 后）再调一次 `auditAll`；
2. **恢复窗口抑制**：维护 `recovering` 集合，advisory 发布时跳过这些车厂，等重建落地再解除——
   顺带消掉 §1 里观察到的抖动；
3. **不去管时机**：巡检每 tick 都重算一遍 advisory（一次遍历 4 条侧线，成本可忽略），
   从根上去掉“什么时候发布”这个问题。

排序建议：3 最省心，1 最保守（只动恢复路径），2 最准（但要引入新状态）。

## 3. ③b 通过：统计取自重建之前

```json
"lastRecovery": { "depot": "2（线路中）", "depotId": "64542daa4ef67d13",
                   "sidings": 1, "trains": 3, "mode": "manual", "at": 1792690584394 }
```

## 6. 定版建议

1. **接口/协议/指令链路可以定版**：选台、发车、回场、压站四条链路本轮全部通过，
   事件、lastPersist、lastRecovery、pathRecoveryNeeded、settings 五处可观测性齐备；
2. **① 建议在 2.0.1 修**，但不阻塞定版：`lastRecovery` 已给出准确的修复时间点，
   外部用它可以覆盖 advisory 的那一个周期；若把验收口径写成「恢复后 ≤1 个巡检周期内收敛」，
   当前实现即满足（实测 ≤10 s 收敛，期间可能抖动一次）；
3. 服务侧 P2⑤（`bridge.mode: telemetry` 只读模式）仍开放，属独立改动，不影响桥接口。
