# 09 · 配置体系与降级策略（七项配置落地版）

本文对应的不是“建议方案”，而是已经编译进 `tsc-dispatch-1.0.0.jar` 的实现：
一个 YAML 文件、七组配置、每项都有对应的运行时代码路径与自检断言。

- 工程：`tsc-dispatch/`（56 个源文件，零第三方依赖，Java 17）
- 模板：`tsc-dispatch/run/config/dispatch.yml`（首次运行自动生成，带注释）
- 校验：`java -jar tsc-dispatch.jar validate`（不改任何状态，退出码即结论）
- 自检：`java -jar tsc-dispatch.jar selftest` —— **67 条断言全绿**

---

## 0. 加载优先级与生效时机

```text
内建默认值  <  配置文件（dispatch.yml）  <  CLI --set  <  POST /v1/config（仅内存）
                ^                                    ^
                |                                    └─ 立即生效，进程退出即失效
                └─ 启动时解析；结构化的三段（dimensions / platform_allow / tiers）只在这里读
```

- **扁平键**：YAML 嵌套被压平成 `a.b.c` 形式，读取时 `-` 与 `_` 等价（`tsc.timeout-ms` 与
  `tsc.timeout_ms` 命中同一个键），所以旧配置习惯不需要改写。
- **结构化三段**：`dimensions` / `platform_allow.rules` / `network_scale.tiers` 保持列表语义，
  不能被 `/v1/config` 覆盖（改结构必须改文件并重启）。
- **校验失败即拒绝启动**：`ConfigValidator` 出现任一 `ERROR` 时进程退出码 2，不带着错的假设去指挥列车。
  运行期异常（端口变了、桥掉了）则走降级，不停机。

## 2. 七项逐条：字段、类型、默认值、处理逻辑

### 2.1 TSC 版本与端口

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `tsc.version.declared` | string | `""` | 运维申报的运行版本（HTTP 面不发布版本号） |
| `tsc.version.min` / `max` | semver | `4.0.0` / `""` | 允许窗口；`max` 为空表示无上界 |
| `tsc.version.strict` | bool | `false` | 越界或未申报时是否拒绝启动 |
| `tsc.port_discovery.enabled` | bool | `true` | 配置端口不通时是否扫描 |
| `tsc.port_discovery.range_start/end` | int | `8888/8898` | 扫描范围（最多尝试 32 个端口） |

**处理逻辑（两层）**：

1. **端口**：先探 `base_url`；失败且允许探测时，按范围逐个换端口重试，命中即改写
   `PortDiscovery.Result.baseUrl` 并写 WARN 日志。原因很具体：模组在配置端口被占用时会向操作系统
   申请空闲端口，服务若死守 8888 会连到一个不存在的进程。
2. **版本**：版本号本身不可信（HTTP 不发布），所以与 **API 指纹** 一起判定：
   `stations/routes` 缺失 → `INCOMPATIBLE`；`route_durations`、`vehicle_identity`、`platforms` 缺失 →
   `DEGRADED` 并关闭对应能力（用坐标估算时长 / 决策降级 advisory / 暂停选台）。
   `strict=true` 且版本越界或未申报 → 直接拒绝启动。

自检：`version gate`（5 条）、`port discovery finds the live port`（2 条）。

### 2.2 控制桥

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `bridge.enabled` | bool | `true` | 总开关 |
| `bridge.mode` | enum | `auto` | `auto` 探测后用；`bridge` 优先；`rcon` 不探桥；`observe` 只读 |
| `bridge.form` | enum | `http` | 形态记录（`http/mod/script`），用于报表与排障 |
| `bridge.base_url` | url | `http://127.0.0.1:8889` | 桥的 HTTP 地址 |
| `bridge.protocol` | int | `1` | 必须 ≥ 1 |
| `bridge.probe_interval_ms` | int | `15000` | 心跳周期 |
| `bridge.offline_after_failures` | int | `3` | 连续失败判离线 |
| `bridge.features_required` | list | `[set_platform]` | 必须具备的指令能力 |

**“桥是否在线”是三级判定**，不是一次 TCP 连通：

```text
GET {bridge.base_url}/dispatch/v1/capabilities
  ├─ HTTP 不可达 / 404 / 超时     → 离线（reason=unreachable）
  ├─ 可达但 protocol < 1         → 离线（reason=protocol）
  └─ 可达且 features ⊇ required  → 在线；否则离线（reason=missing-features）
```

半在线（能连但缺能力）必须算离线，否则服务会下发一个桥根本不认识的指令，然后误以为成功。

自检：`bridge failure falls back to RCON`、`dimension isolation`（桥关闭时走原版遥测）。

### 2.3 RCON

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `rcon.enabled` | bool | `true` | 开关 |
| `rcon.password` | string | `""` | 为空则**即使 enabled 也不可用** |
| `rcon.fallback_on` | list | `bridge_offline,bridge_reject,command_timeout` | 触发兜底的故障类型 |
| `rcon.commands.*` | string | 见模板 | 命令模板，`{depot}` 会被替换 |

**何时降级到 RCON**（`FailoverActuator`）：

| 触发 | 条件 | 结果 |
|---|---|---|
| `bridge_offline` | 桥心跳失败 / 启动探测失败 | 该维度改用原版遥测；RCON 承接它能做的指令 |
| `command_timeout` | 桥调用抛异常（`retryable=true`） | 先标记桥离线，再按策略转 RCON |
| `bridge_reject` | 桥返回 `ok=false, retryable=false` | 按策略决定“转 RCON”还是“直接失败上报” |
| `manual` | 人工 `POST /v1/command` | 仍走同一链路，便于手工强制重置 |

RCON 只能承载三种粗粒度指令（`refresh_depot_routes / instant_deploy / clear_depot`）。
逐车指令（`set_platform / reroute / return_to_depot`）在 RCON 模式下 `supports()` 返回空，
`CommandBus` 直接判 `ADVISORY`，不会假装已执行。

### 2.4 维度

| 字段 | 类型 | 说明 |
|---|---|---|
| `dimensions[].id` | string | 维度标识，仅用于日志与报表 |
| `dimensions[].index` | int | **实际发给 `?dimension=` 的索引**，跟随宿主加载顺序，不能从 id 推断 |
| `dimensions[].enabled` | bool | 关闭的维度不创建运行时 |

**隔离方式**：每个启用维度一个 `DimensionRuntime`，各自持有

- 世界模型快照与遥测源（桥可用时用桥，否则用该维度的 `/mtr/api/map/*?dimension=N`）；
- 独立 `LeaseTable`（站台/车厂租约不跨维度）；
- 独立 `CommandBus`（序号、幂等键、状态目录 `state/dim-<index>/`）；
- 独立健康状态与自适应轮询间隔。

共享的只有 HTTP 连接池和执行器（一个进程只有一个控制台）。

自检：`dimensions run isolated runtimes`（4 条：两个运行时、两套遥测、健康聚合、状态不共享）。

### 2.5 网络规模与自适应轮询

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `network_scale.max_trains` | int | `30` | 预期同时在线列车数，用于选初始档位 |
| `network_scale.tiers[].max_trains/interval` | list | 10→1000 / 40→2000 / ∞→4000 | 分档表 |
| `network_scale.adaptive` | bool | `true` | 是否随实测调整 |
| `network_scale.polling_min/max_ms` | int | `500 / 10000` | 硬边界 |

**调度策略**：

```text
base = 第一个满足 max_trains >= network_scale.max_trains 的档位
每轮结束后：
  latency > interval/2        → interval *= 1.5      （服务器扛不住，放慢）
  observed > expected         → interval *= 0.8      （比预期更忙，加快）
  interval > base             → interval = max(base, interval*0.9)   （向基线回归）
  interval < base             → interval = min(base, interval*0.9+1)
  interval = clamp(interval, polling_min_ms, polling_max_ms)
```

注意 `observed > expected` 是“比申报规模更忙”，此时加快采样而不是放慢——这正是配置里
`max_trains` 被低估时的兜底。轮询循环用“自调度”（每轮结束后按当前间隔排下一次），
而不是 `scheduleAtFixedRate`，否则间隔无法动态变化。

自检：`tiers and clamps drive the poll interval`（5 条）。

### 2.6 目标函数与硬约束

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `dispatch.strategy` | enum | `balanced` | `on_time` / `min_waiting` / `balanced` |
| `dispatch.weights.*` | double | 空（继承预设） | `travel/occupancy/wait/depot/deviation` |
| `dispatch.constraints.route_priority` | map | `{}` | 线路（编号或 hex）→ 优先级倍数 |
| `dispatch.constraints.depot_capacity[_limit]` | int | `0`（不限） | 车厂容量硬上限，可按车厂覆盖 |
| `dispatch.constraints.max_hold_seconds` | int | `0` | 允许主动压车的上限 |

预设权重：

| 策略 | travel | occupancy | wait | depot | deviation |
|---|---|---|---|---|---|
| `on_time` | 1.0 | 0.8 | 0.25 | 0.3 | 1.0 |
| `min_waiting` | 1.0 | 1.2 | 1.4 | 0.5 | 0.1 |
| `balanced` | 1.0 | 1.0 | 0.6 | 0.4 | 0.2 |

**权重如何进入算法**：

```text
edgeCost(e, t) = travel(e)/priority(route(e)) * w.travel
               + max(0, freeAt(e.to,t) - t)/1000 * w.wait
               + (busy ? min(900, 60 + waitSeconds) : 0) * w.occupancy
               + (e.to ∈ avoid ? 900 : 0)
               + (e.to 是车厂 ? travel(e)*(w.depot - 1) : 0)
```

- **线路优先级**同时影响两处：① 规划时高优先级线路的边更“便宜”；② 站台冲突时
  高优先级列车不让行（`priorityOf(other) < myPriority → 不视为冲突`）。
- **车厂容量**是硬约束，不是惩罚项：先过滤掉已满的车厂再规划；所有车厂都满时报
  `ADVISORY “every reachable depot is at capacity”`，不下发指令。
- 占用惩罚有上限（900 s）是刻意的：**永远要有可行解**，否则规划器会返回空、服务卡死。

自检：`depot capacity is a hard constraint`（3 条）、`planner prefers the cheaper of two routes`。

### 2.7 站台允许集合

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `platform_allow.default` | enum | `allow` | 无匹配规则时的默认策略 |
| `platform_allow.rules[]` | list | 见模板 | `{route, station, platforms[], deny}` |
| `platform_allow.rules[].route` | string | — | 线路**编号**（`"A"`）、线路 hex、或 `"*"` |
| `platform_allow.rules[].station` | string | — | 车站 hex 或 `"*"` |
| `platform_allow.rules[].platforms` | list | — | 站台 hex 列表，支持 `"*"` |
| `platform_allow.rules[].deny` | bool | `false` | false=白名单，true=黑名单 |

**匹配语义**（可预测，不玩花活）：

1. 收集所有 `(route, station)` 匹配的规则；
2. 一条都没有 → 用 `default`；
3. 有匹配 → 命中任一白名单且在**所有**黑名单之外才算允许。

**校验链路有三道**，任何一道都能拦住违规指令：

```text
① PlatformSelector 选台时过滤候选
② Dispatcher 生成决策后再查一次（配置可热更新，防止窗口期漏网）
③ CommandBus 下发前再核一次前置条件（平台/车辆状态是否还成立）
```

第 ② 道不通过时不会有命令产生，只记 `dispatch_skipped_total{reason=platform_not_allowed}`
和一条 INFO 日志（车辆、线路、被拒站台），便于发现“规则写错了”而不是“服务没反应”。

自检：`platform allow-set blocks an illegal move`（2 条：无规则时放行、有规则时抑制）。

## 3. 关键伪代码（Java，实际实现）

### 3.1 加载与校验

```java
// Main.loadConfig
Path path = Path.of("config/dispatch.yml");
if (!Files.exists(path)) Config.writeTemplate(path);      // 首次运行落模板
Config config = Config.load(path);                        // YAML → 扁平键 + 结构化三段
for (String setting : cliOverrides) config.override(k, v); // --set

// Service.start —— 先校验，再连网
List<Issue> issues = ConfigValidator.validate(config);
if (ConfigValidator.hasErrors(issues)) {
    throw new IllegalStateException("configuration rejected: " + issues);
}
if (config.getBool("tsc.version.strict") && config.get("tsc.version.declared").isBlank()) {
    throw new IllegalStateException("strict mode needs tsc.version.declared");
}
```

### 3.2 站台允许集合校验

```java
// PlatformSelector：先过滤候选，避免选出非法台
List<Platform> candidates = new ArrayList<>();
for (Platform p : snapshot.platformsOf(vehicle.stationHex)) {
    if (policy == null || policy.allows(vehicle.routeHex, vehicle.routeNumber,
                                        vehicle.stationHex, p.hex())) {
        candidates.add(p);
    }
}
if (candidates.size() <= 1) return Choice.unchanged("no platform allowed by platform_allow");

// Dispatcher：生成决策后再核一次（配置可热更新）
if (!config.platformPolicy().allows(vehicle.routeHex, vehicle.routeNumber,
                                    vehicle.stationHex, chosen)) {
    metrics.inc("dispatch_skipped_total{reason=platform_not_allowed}");
    Log.info("platform rejected by allow-set",
             "vehicle", vehicle.id, "route", vehicle.routeHex, "platform", chosen);
    continue;    // 不生成 Command，因此不会有任何指令下发
}
```

`PlatformPolicy.allows` 的完整语义：

```java
public boolean allows(String routeHex, String routeNumber, String stationHex, String platformHex) {
    if (rules.isEmpty()) return defaultPolicy == ALLOW;
    boolean matched = false, allowed = false;
    for (PlatformRule rule : rules) {
        if (!rule.matches(routeHex, routeNumber, stationHex)) continue;
        matched = true;
        if (rule.deny() && rule.contains(platformHex)) return false;   // 黑名单立即否决
        if (!rule.deny() && rule.contains(platformHex)) allowed = true;
    }
    return matched ? allowed : defaultPolicy == ALLOW;
}
```

### 3.3 控制桥探测、识别与故障转移

```java
// Service.resolveChannels —— 启动时
Actuator rcon = config.rconEnabled() ? new RconActuator(config) : null;
BridgeSource bridge = config.bridgeEnabled() ? new BridgeSource(config, http, dim0) : null;
boolean usable = bridge != null && bridge.probe() && meetsRequirements(bridge);

Actuator bridgeActuator = usable ? new BridgeActuator(config, http, bridge.features()) : null;
FailoverActuator failover = new FailoverActuator(bridgeActuator, rcon,
                                                 config.rconFallbackOn(), metrics);
if (!usable) failover.markBridgeOnline(false, "bridge not usable");

boolean meetsRequirements(BridgeSource b) {
    if (b.protocol() < 1) return false;                                   // 协议不匹配
    if (config.getBool("bridge.require_vehicle_telemetry") && !b.vehicleTelemetry()) return false;
    return b.features().containsAll(config.bridgeFeaturesRequired());     // 缺能力
}

// Service.heartbeat —— 每 probe_interval_ms
failover.markBridgeOnline(bridge.probe() && meetsRequirements(bridge),
                          ok ? "probe ok" : "probe failed");

// FailoverActuator.execute —— 每条指令
if (bridgeOnline && bridge.supports(kind)) {
    Result r = bridge.execute(command);
    if (r.success()) return r;
    if (r.retryable()) markBridgeOnline(false, r.detail());   // 连接类故障 → 判离线
    if (allowFailover(r)) { /* 转 RCON */ }
    else return r;
}
if (rcon != null && rcon.supports(kind)) return rcon.execute(command);
return Result.fatal("no channel available for " + kind);       // 绝不假装成功
```

## 4. Fail-safe：缺什么、坏什么、怎么退化

总原则：**配置错误停机，运行错误降级**。停机是为了不带着错误假设发指令；降级是为了让运维还能看见状态。

| 异常 | 检测点 | 服务行为 | 对外可见 | 自愈 |
|---|---|---|---|---|
| YAML 语法错误 | `Yaml.parse` | 启动失败，打印行号 | 退出码 2 | 改文件 |
| 字段越界/冲突（端口、URL、重复维度、min>max…） | `ConfigValidator` | 启动失败 | `validate` 报告 + 退出码 2 | 改文件 |
| `strict` + 版本越界/未申报 | `Service.start` | 启动失败 | 退出码 2 | 改 `declared`/窗口 |
| 非 strict 版本越界 | `CompatibilityProbe` | 继续运行，能力按指纹裁剪 | `/v1/dimensions → level=DEGRADED` | 改配置 |
| 端口被模组换掉 | `PortDiscovery` | 扫描范围，连上真实端口 | `/healthz.baseUrl`、WARN 日志 | 自动 |
| 范围内都不通 | `PortDiscovery` | 保持原 `base_url`，遥测 FAILING | `/readyz` 503 | 每轮重试 |
| 桥离线 | 启动探测 + 心跳 | 执行器切 RCON；无 RCON 则 observe；逐车决策 `ADVISORY` | `/v1/channels.actuator.active` | 心跳恢复后自动切回 |
| 桥可达但缺能力 | `meetsRequirements` | 视为离线，记录 reason | `bridgeOnline=false` | 升级桥 |
| 桥拒绝且不允许兜底 | `FailoverActuator` | 指令 `FAILED`，释放租约 | `/v1/decisions.status=FAILED` | 人工 |
| RCON 未配置 | `config.rconEnabled()` | 不构建执行器，仅 observe | 启动 WARN（实测见到） | 配 `password` |
| RCON 指令失败 | `RconActuator` | 重试后 `FAILED` | 同上 | 人工 |
| 车厂满 | `DepotCapacity` | 不下发回场指令，换车厂；全满则 advisory | `/v1/decisions.reason` | 车开走自然恢复 |
| 站台规则写错（未知 id） | 规则校验 + 运行时过滤 | 该台不可选，日志点名 | `platform_not_allowed` 指标 | 改配置 |
| 维度索引写错 | 首轮请求 400 | 该维度 FAILING，其它维度不受影响 | `/v1/dimensions` | 改 `index` |
| 实测规模超预期 | `adapt()` | 缩短轮询间隔至下界 | `metrics.telemetry_interval_ms` | 自动 |

**为什么“桥离线”不会让服务雪崩**：`FailoverActuator` 只影响写通道，读通道每轮独立判定；
一个维度掉线不影响另一个维度（各有 `DimensionRuntime`）；管理面永远独立于游戏连接，
正是 TSC 挂掉时最需要的那个界面。

## 6. 与旧版 `.properties` 的兼容

- 若 `--config` 指向 `.properties`，仍可加载：键被压成同一套扁平键，结构化三项取默认值。
- 键名 `-` 与 `_` 等价：`tsc.timeout-ms` 与 `tsc.timeout_ms` 是同一个键。
- 迁移建议：先跑 `validate` 比对告警，再把文件换成 YAML 模板；结构化配置（维度分档、
  站台规则、规模分档）只有 YAML 能表达。
