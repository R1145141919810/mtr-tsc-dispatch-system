## 0. 结论

```text
主项 deploy_train(car, platform)   ❌ 仍未发车，但失败方式变了：
                                      现在返回 APPLIED（exec+1），车却被宿主删掉
回归 普通 deploy                    ✅ 1 s 内 onRoute=true
回归 dwell_control                  ✅ 不崩、到期释放、tickFailures=0
路径落盘 persistPath                ❌ 重启后该侧线仍是 pathLost
```

**静默问题解决了，但换成了“假成功”**：桥报 applied，车没走，被启动的那辆车在整个世界里找不到。

## 1. 主项：带目标 deploy

```text
deploy_train(-78562, 9A0CFD)
→ deferred "path regenerated; departure queued on siding 6b6eacc355ec212f"

t+1s diag=s0  id=-68665 run=False speed=0  exec=0 failed=0 pending=1  lastErr=''
t+2s diag=s0  id=-68665 run=False speed=0  exec=0 failed=0 pending=1  lastErr=''
t+3s diag=[]  id=881531 run=False speed=0  exec=2 failed=0 pending=0  lastErr=''   ← 两次 applied
t+4..10s       id=881531 run=False speed=0

之后全表检查：
  被启动的 -68665 …… 在世界里已不存在（0 条）
  同侧线出现新车 -51125（停场）
```

`exec=2` 的两次分别是：路径就绪（applied “path ready via 策略0”）与排队发车（applied）。
也就是说 **depart() 返回了成功，但宿主在随后的 simulate 里把这辆车删了**（id 直接消失），MTR 又补了一辆停场车。
清单预期“若仍失败一定会有 failed 事件”——这次没有 failed，而是 **false APPLIED**。

### 1.1 决定性对照

对那辆新车再发一次**普通 deploy**（无目标）：

```text
deploy_train(881531) → deferred "departure queued"
t+1s run=True speed=3.8
t+3s run=True speed=12.0
t+5s run=True speed=16.7
```

**1 s 就发车。** 同一侧线、同一辆车、同一个 depart() 实现，唯一差别是：
带目标的那次是在**路径就绪的同一 tick** 立刻 startUp，普通 deploy 则在几秒后。

结论：**depart 本身没坏；“刚被 re-create 出来的车立刻 startUp” 才是问题。**
宿主对“同一 tick 内重建 + 立刻启动”的处理是丢弃该车实例并重新生成。

## 2. 路径落盘：仍未生效

本轮把 writePathCache() 包了一层 persistPath，只在路径非空时调用。重启后检查：

```text
id=-86837 siding=0a7783 planned=4ad410  lost=False   ← 未动过的
id=804277 siding=6b6eac planned=''      lost=True    ← 本次重生成过
id=-10365 siding=a37272 planned=''      lost=True    ← 本次未直接操作过
id=859109 siding=9d163c planned=4ad410  lost=False   ← 未动过的
```

重生成过的侧线重启后 **依旧 pathLost**；另外 a37272 本轮没被直接重生成，也变成 lost
（可能是车厂/存档层面的连带影响，建议下轮单独验证）。

它们在代码里承认的风险（§4.1：“persistPath 返回 false，目前未上报”）正好对上：
**persistPath 很可能静默失败**，而外部完全看不出来。

## 4. 建议（按优先级）

### P0 · 不要让“未发生的发车”返回成功

depart() 现在只看 startUp 有没有抛异常。请在**下一个 tick 做后置校验**：

```java
// completePendingDeparture 之后，把这次 departure 记进 pendingVerification
// 下一 tick：按 id 找车
if (vehicle == null)              → failed("departed vehicle was dropped by the host");
else if (!vehicle.getIsOnRoute()) → failed("departure did not take effect");
else                              → applied("departed, verified on route");
```

否则外部（含调度服务）会把“车没动”当成“已发车”，这比失败更难排查。

### P0 · 不要在“路径就绪的同一 tick”发车

实测同一 tick 内 startUp 会被宿主丢弃，而延迟几秒后再 depart 100% 成功。
建议：路径就绪时只标记 readyAt = now，把真正的 depart 放到 now + 1000~2000 ms 之后的 tick，
并在那里做 §P0 的后置校验。这与“普通 deploy 能成功”的时序完全一致。

### P1 · 把 persistPath 的结果暴露出来

persistPath 返回 boolean，但现在没人看。建议 /health 增加：

```text
lastPersist: { siding, ok, at, method }     ← ok=false 时同时写 lastError
```

本次重启后路径仍然丢失，最可能就是它返回了 false。另外 writePathCache 是宿主包私有方法，
建议顺带记录“反射是否命中”（命中/未命中各一条日志），否则宿主升级后只会静默失效。

### P1 · 补一个“发车事件回放”

本次唯一拿不到的关键信息是 applied 事件的原文（里面带
"departed on timetable slot N (t+0, timetable=M)"）。建议 /health.events 保留最近 20 条
（kind / target / outcome / message / at），这类问题下一次就不用再猜了。

再补一个“下一 tick 后置校验 + 延迟 1–2 s 发车”，这条链路就能闭环。**
