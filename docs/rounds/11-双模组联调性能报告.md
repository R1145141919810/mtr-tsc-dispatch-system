# 11 · 双模组联调性能报告（真实线网）

环境：Forge 47.4.23 专用服务端 · Minecraft 1.20.1 · MTR **4.0.5** · 控制桥 **1.1.0**（已按上一轮建议优化）· 调度服务 1.0.0
世界：用户存档（2 条线路 / 4 条独立轨道 / 3 站 / 12 站台 / 2 车厂 / 4 列车）

---

## 1. 线网实况（由桥遥测读出，非猜测）

```text
站点1 = 521c265053465583    站点2 = ce1d84bdf4543934    站点3 = 7bcb6bc01ca30324

线路1（一端车厂）||上行   站点1/1 → 站点2/1 → 站点3/1   durations 10.43 / 11.75 / 17.87 s
线路1（一端车厂）||下行   站点3/2 → 站点2/2 → 站点1/2   durations 11.75 / 10.43 s
线路2（中部车厂）||上行   站点1/3 → 站点2/3 → 站点3/3   durations 10.67 / 11.75 / 18.11 s
线路2（中部车厂）||下行   站点3/4 → 站点2/4 → 站点1/4   durations 11.75 / 10.43 s

车厂 1（线路头）：2 条侧线     车厂 2（线路中）：2 条侧线
```

两个直接结论：

1. **上行方向多出一条 duration**（3 段时长对应 3 个停靠站 = 只有 2 段区间），多出来那条就是**折返/入库腿**。
   这条信息过去被服务忽略，导致“从任何一站回库都按 150 s 估”。
2. **维度顺序又变了**：本世界是 `overworld → the_nether → the_end`，
   上一轮那个世界是 `overworld → the_end → the_nether`。同一个模组版本、不同存档，顺序不同——
   所以 `dimensions[].index` 只能照抄 `capabilities.dimensions`，不能写死。

## 2. 性能数据

### 2.1 单次调用延迟

| 调用 | 平均 | 最差 | 样本 |
|---|---|---|---|
| 桥 `GET /dispatch/v1/state?dimension=0`（12 站台 / 4 线路 / 2 车厂 / 7 车） | **6.1 ms** | 41.1 ms（首次冷调用） | 10 |
| 服务 `GET /v1/status` | 2.6 ms | 3.2 ms | 5 |
| 命令往返 `POST /dispatch/v1/command`（`dwell_control`） | **3.0 ms** | — | 1 |

### 2.2 持续运行（1 Hz 轮询，60 s 采样）

| t(s) | polls | vehicles | 桥 executed | 桥 failed | 桥 deferred |
|---|---|---|---|---|---|
| 0 | 155 | 7 | 5 | 3 | 4 |
| 30 | 185 | 7 | 5 | 3 | 4 |
| 60 | 205 | 7 | 5 | 3 | 4 |

- 轮询严格 1 Hz（10 次/10 s），无丢拍、无堆积。
- 桥计数器全程不变（没有决策时确实不发指令）。
- **服务 CPU：60 s 内 0.4 s（≈0.7%）**，RSS 99 → 101 MB。
- **服务端 CPU：60 s 内 0.8 s（≈1.3%）**，RSS 2.18 → 2.16 GB（MTR 自身基线，与桥/服务无关）。

### 2.3 4 倍压力（250 ms 轮询，30 s）

```text
polls in 30s: 114  (3.8/s，目标 4/s)
server cpu +0.3s   service cpu +0.4s
state latency: avg 3.9 ms  max 18.8 ms   ← 比 1 Hz 时还低
```

**结论：这条线网的规模（12 站台 / 7 车）下，桥与服务几乎没有可测开销；4 Hz 轮询仍有余量，**
瓶颈不在两者。若线路数上到几十条、车辆上百，再考虑桥端加 `version/ETag` 与状态差量推送（见 §5）。

## 4. 发现的桥缺陷（P1，本轮新）

**`regenerateTo` 把“要改台的那列车自己”算成了“占用中的列车”。**

```java
if (activeVehicles(siding) > 0) {
    return BridgeResult.rejected(..., "siding " + siding.getName()
        + " still has active trains; regenerating would drop them", now);
}
```

`activeVehicles(siding)` = 该侧线内的**全部**车辆，包括停在侧线、正等着被重新生成路径的那一列。
于是只要车还在侧线里（也就是唯一需要改台的场景），命令必然被拒：

```text
deploy_train(859109 -> 430a53)  → rejected "siding 1 still has active trains"
set_platform(859109 -> 430a53)  → 同上
deploy_train(859109, 无目标)     → deferred → 正常发车
```

这直接废掉了桥对外宣称的 `set_platform` 能力，也是服务唯一“停场车选台”的落地路径。
建议改为：只把**非本车**的在途车辆算作活跃，或调用
`activeVehicles(siding) > (vehicle.getIsOnRoute() ? 1 : 0)`，并在“确有在途车”时才拒绝。

其余仍成立的建议（上一轮 4.1–4.7 已修/已验证的部分不再列出）：

1. `return_to_depot` 的 `sidingId` 目前仍未参与真正停车选址（只做 `parkAndHold`），建议实现或从契约删掉。
2. `dwell_control` 现在有 `autoReleased` 计数，很好；再补一个“当前持有列表”便于排障。
3. `state.version` 已有，但只能全量比对；建议支持 `?since=` 或 ETag 304，为大规模线网留余量。
4. 建议 `capabilities` 增加 `minPollIntervalMs`，让服务端能主动告诉调用方“别比这个更频繁”。

## 5. 服务侧本轮改动

| 改动 | 原因 |
|---|---|
| 优先使用 `nextStationId`（semantics 2） | 桥现在显式给出“下一站所属车站”，比用平台反查更准 |
| 折返腿建模：`durations.size == stops.size` 时，用最后一条时长作为入库时间，且车厂只连**两端终点站** | 此前“任何站回库 150 s”过于乐观；实测该线网两端入库 17.9 s、中间站需经终点折返 38.3 s |
| 兼容 `semantics` / `loading` / `dimensions[{index,id}]` | 新桥字段 |

折返腿建模前后对比（同一站，规划到最近车厂）：

```text
改前：站点1 / 站点2 / 站点3 → 车厂  全部 150.0 s（假直连）
改后：站点1 → 17.9 s   站点2 → 38.3 s（经终点折返）   站点3 → 17.9 s
```

这直接影响“定时回场”的决策时机：过去会在离库很远的站就判定“回库很便宜”，现在不会。

## 6. 仍未覆盖

1. **选台链路**因 §4 的缺陷无法在真机闭环；修复后可复测。
2. **定时回场**：本轮 `return_after_seconds=0` 关闭，避免打乱性能采样；回场链路仍只有单元级验证。
3. **大规模**：12 站台 / 7 车属于小网，结论不能外推到上百车；压测建议用合成车队（桥侧加 `dryRun` 注入）。
4. 服务侧尚未消费 `capabilities.dimensions` 做配置自校验（应加：启动时比对 `index/id`，不一致直接报错）。

---

## 7. 一句话结论

**协议、时延、开销三项都过关：状态 6 ms、指令 3 ms、服务 0.7% CPU，4 Hz 轮询仍有余量。**
真正卡住功能的是桥里一行“侧线占用”判定——它让 `set_platform` 在最需要的场景下必然被拒。
修掉这一行，这条线网上的选台/避让就能完整跑通。
