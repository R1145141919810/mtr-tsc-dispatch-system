## 0. 一句话结论

整改确实解决了上一轮的“侧线占用误判”和“维度不可校验”，但复测又挖出**两个新的阻断问题**：
**`dwell_control` 在 MTR 4.0.5 上会直接把服务器 tick 打崩**，
**路径重生成后的列车无法发车**（重建成功、发车永不生效）。

## 2. P0 · `dwell_control` 打死服务器

### 2.1 事实

```text
POST /dispatch/v1/command  {"kind":"dwell_control","vehicleId":"-86837…","args":{"seconds":30}}
→ { "outcome":"applied", "message":"dwell hold set" }

GET /dispatch/v1/health → holds: [{ vehicle:-86837…, remainingSeconds:30 }]

（下一 tick）
→ Exception in server tick loop → crash-2026-10-22_23.20.23-server.txt
   serverTime 在随后 4 s 内只前进了 100 ms（服务器主循环已死，TSC 模拟线程仍在独立走）
```

### 2.2 根因（用宿主字节码核对）

```text
javap org.mtr.core.generated.data.VehicleSchema
  protected long elapsedDwellTime;      ← long

mtbridge GameActions.holdDwell:
  Reflect.setDouble(vehicle, "elapsedDwellTime", 0.0);   ← 写 double
```

`Field.setDouble` 对 `long` 字段抛 `IllegalArgumentException`；`Reflect.setDouble` 把它包成 `IllegalStateException` 抛出；
`BridgeService.tick` 的 `dwellHolds.forEach` 没有 try/catch → 异常穿出 `onServerTick` → Forge 判定 tick 崩溃 → 服务器关停。

### 2.3 建议修法（三行）

```java
// GameActions.holdDwell —— 按字段真实类型写
Object current = Reflect.get(vehicle, "elapsedDwellTime");
if (current instanceof Long) Reflect.setLong(vehicle, "elapsedDwellTime", 0L);
else Reflect.setDouble(vehicle, "elapsedDwellTime", 0.0);
```

另外两处必须补：

1. **`BridgeService.tick` 整体包 try/catch**：一个车辆字段写失败不能带走整个服务器 tick。
   桥是“外部控制面”，任何异常都应在桥内变成 `failed++` 与 `lastError`，绝不能冒泡到宿主 tick。
2. `dwellElapsed` 的读取同理（`Reflect.getDouble` 读 `long`），当前恰好返回 0，但字段一变类型就又是坑。

### 2.4 影响范围

`dwell_control` 是**运行中列车唯一可用的杠杆**（改台对运行车无效）。它一崩，
“压站避让”整条链路就不可用，而且崩的是整个服务器，不是桥自己。

## 3. P1 · 路径重生成后列车无法发车

### 3.1 事实（均在崩溃之前、干净服务器上取得）

```text
set_platform(859109…, 430a53)
→ deferred（不再被拒）
→ 3 s 后 id 变为 826405…（重建成功）
→ deploy_train(826405…) → deferred "departure queued"
→ 16 s 后仍 inDepot=true, speed=0

deploy_train(804277…, 9a0cfd)
→ deferred "path regenerated; departure queued on siding 6b6e…"
→ id 变为 507942…，12 s 内未驶出

对照：未做重生成的停场车 deploy_train(无目标) → 2 s 后 run=true, speed=7.8 → 正常驶出
```

### 3.2 判断

重生成（`generateRoute`）确实把车重建了，但重建后的车**没有可用的发车槽/路径**：
`GameActions.depart` 把 `departureIndex` 钳到 0 后调 `startUp`，`startUp` 不抛异常但车辆并未真正上线，
随后被宿主按“无路径”处理，表现为一直停场。

这与“车厂重生成会重建时刻表”的宿主机制一致：**只有车厂级生成（`Depot.generateDepots`）才会给车辆分配有效的 `departureIndex`**，
单条 `Siding.generateRoute` 只生成几何路径。

### 3.3 建议

1. `generateRoute` 之后不要立刻宣布“可发车”；在 telemetry 里给 `pathReady` 字段
   （判定：`vehicleExtraData.immutablePath` 非空且 `nextPlatformId != 0`）。
2. 发车意图改为“等到 `pathReady` 再 depart”，而不是固定 1 s。
3. 若宿主支持，重建后调用一次车厂级生成（哪怕只针对该 depot），否则明确文档化为
   “重生成仅重建路径，发车需等下一次车厂生成”。
4. `nextPlatformId` 对停场车恒为 0，导致清单第 2 项无法验收；建议对停场车输出
   “计划首站台”（读 siding path 的第一个 PathData 平台），让调用方能验证选台结果。

## 4. P1 · `?since=` 永远得不到 304

```text
stateVersion(simulator) = simulator.getCurrentMillis()   ← 是时钟，不是内容版本
state?since=<上次 version> → 200（两次调用间 version 前进 349 ms）
```

版本号只要随模拟时钟走，就必然大于 `since`，304 分支永远进不去。
建议：用内容摘要（对去掉 `serverTime/version` 后的 body 做 hash）或“只在车辆/站台状态变化时自增的 revision”。

## 5. 观察 · 维度顺序在两次启动之间变了

同一个存档、同一个 jar，两次启动读到的顺序不同：

```text
第一次： [minecraft/overworld, minecraft/the_nether, minecraft/the_end]
第二次： [minecraft/overworld, minecraft/the_end, minecraft/the_nether]
```

说明 `WORLD_ID_LIST` 的构建依赖宿主遍历顺序，不是稳定值。**用 index 钉维度是不可靠的**。
现在的“启动即校验、强制模式退出码 2”是对的（清单第 8 项已验证），但体验上会每次重启都可能挡一次。

建议下一步二选一：

- 服务侧：配置里写 `id` 为主键，启动时按 id 反查 index 并**自动重映射**（仅当 id 唯一命中）；
- 桥侧：让 `dimensions[].index` 成为“稳定槽位”（例如按 id 排序后编号），而不是宿主遍历序。

## 7. 复测结论与建议优先级

| 优先级 | 事项 |
|---|---|
| **P0** | `holdDwell` 按字段真实类型写；`tick` 整体 try/catch，异常不得穿出宿主 tick |
| **P1** | 重生成后的发车链路（等 `pathReady` 或触发车厂级生成）；停场车输出“计划首站台” |
| **P1** | `?since=` 改成内容版本，否则该优化等于没做 |
| **P2** | 维度 index 稳定化（或服务侧按 id 重映射） |
| **P2** | 清单第 3 项的“两辆停场”分支在本网络不可达，建议补一个可构造该场景的测试指令（如 `hold` 一辆在场车） |

修完 P0 后建议立刻回归“压站避让 + 发车”两条链路；P0 不修，任何涉及 `dwell_control` 的测试都会以服务器崩溃收场。
