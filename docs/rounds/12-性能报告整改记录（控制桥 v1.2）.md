## 1. P1 核心缺陷：侧线占用判定把目标车自己算进去了

### 1.1 根因（用字节码确认，不是猜）

`javap -c` 显示 `Siding.generateRoute` 的第一条指令就是清空车辆集合：

```text
0: aload_0
1: getfield  #107  // Field vehicles:ObjectArraySet
4: invokevirtual ... ObjectArraySet.clear:()
```

所以“侧线里有车”确实是危险信号——但危险的对象是**别人**，不是要被改台的那列车。

### 1.2 报告建议不能照抄的原因

报告建议改成 `activeVehicles(siding) > (vehicle.getIsOnRoute() ? 1 : 0)`。
问题：目标车自己也会被 `clear()` 掉，随后由 `simulateTrain` 用新车厂路径**重新生成**（新 id）。
这不是 bug，而是宿主自己的车厂重生成机制。所以判定要按“会不会伤到别人”来写，而不是按数量写。

### 1.3 现在的实现

```java
boolean otherRunning = false;
int otherParked = 0;
for (Vehicle candidate : vehicles(siding)) {
    if (candidate == self) continue;               // 目标车本来就要被重建
    if (candidate.getIsOnRoute()) otherRunning = true;
    else otherParked++;
}
if (otherRunning) return rejected("another train in siding X is running; regeneration would drop it");
if (otherParked > 0) return rejected(otherParked + " other parked train(s) share siding X; ...");
siding.generateRoute(platform, null, -1, cruisingAltitude(siding));
return deferred("... the parked train is re-created with the new route once the path settles "
              + "(its vehicle id may change - re-read state before the next command)");
```

三档语义：

| 侧线里有什么 | 结果 |
|---|---|
| 只有目标车 | ✅ 允许重建；车被重建、id 可能变化 |
| 目标车 + 另一列**在途**车 | ❌ 拒绝（会把运行中的车清掉） |
| 目标车 + 另一列**停场**车 | ❌ 拒绝（会把无关的停场车也清掉） |

### 1.4 连带修复：发车意图改挂“侧线”而不是“旧车 id”

重建后车辆 id 会变，若仍按旧 id 排发车意图，车永远发不出去。现在：

```java
if (siding != null) {
    queueSiding(siding.getId(), command, now, now + 15_000L, source);   // key = "siding:<id>"
}
// tick 中：解析 siding → 取该侧线第一辆车 → 等 1s 让路径收敛 → depart
```

于是 `deploy_train(train, platform)` 在“重建 + 发车”这条链上是自洽的：车被重建，随后由侧线意图发出。

## 2. 其余建议

| 报告项 | 处理 |
|---|---|
| §4.1 `return_to_depot` 的 sidingId 不参与选址 | MTR 的车辆只能回自己的侧线，跨股道要重建那条侧线（会清空在途车）。所以保留参数但**改成断言语义**：指向别的股道 → `REJECTED`；成功时 `effectiveAt/target` 回填**实际**侧线 id，调用方不必猜 |
| §4.2 补“当前持有列表” | `/dispatch/v1/health.holds:[{vehicle, releaseAt, remainingSeconds}]`，时间用模拟器时钟，避免与墙钟混用 |
| §4.3 `state` 只能全量比对 | 新增 `?since=<version>`：`version <= since` 直接 304，与 `If-None-Match` 等价 |
| §4.4 缺 `minPollIntervalMs` | `capabilities.minPollIntervalMs = 250`；服务侧读到后若高于 `network.polling_min_ms` 就上调下限并打日志 |
| §6.4 服务未消费 `capabilities.dimensions` | 服务启动时逐个比对配置的 `index/id`，不一致记 ERROR；`actuator.mode=bridge`（强制桥）时直接拒绝启动 |

服务的自校验实现：

```java
for (DimensionSpec spec : config.enabledDimensions()) {
    if (spec.index() >= ids.size() || ids.get(spec.index()).isBlank())
        issue("bridge has no dimension at index " + spec.index());
    else if (!ids.get(spec.index()).equals(spec.id()))
        issue("index N: config id X != bridge id Y");
}
if (mismatch && "bridge".equalsIgnoreCase(mode)) throw new IllegalStateException(...);
```

这正是本报告 §1 两次“维度顺序不同”踩到的坑——现在配置写错会在启动时就被挡下，而不是把指令发到别的地牢。

## 3. 未做 / 仍需验证

1. **跨股道回场**：技术上不可行（见 §2），契约里改为“断言 + 回填实际值”，没有假装实现。
2. **选台链路真机复测**：修复后应能跑通“停场车 → `set_platform` 换个台 → 车被重建并停在新路径上”，
   但本轮无法在本地起服，需在你的存档上复测（见 §4）。
3. **大规模**：报告已证明 12 站台/7 车下无压力；上百车仍建议用 `dryRun` 合成。

## 4. 复测清单（针对本轮改动）

1. `/dispatch/v1/capabilities` → 出现 `minPollIntervalMs:250` 与 `dimensions[{index,id}]`；
2. 停一辆车在库，发 `set_platform` 到另一站台 → 不再出现 “still has active trains”，
   返回 `deferred`，1–2 s 后 `state` 里该车 id 变化且 `nextPlatformId` 为新台；
3. 同侧线再停一辆车，重复上一步 → 应返回 `rejected "1 other parked train(s) share siding ..."`；
4. `deploy_train(train, platform)` → 重建 + 由侧线意图发车，车真正驶出；
5. `return_to_depot(train, 别的股道 id)` → `rejected`；发自己的股道 → `deferred`，回库后被 hold；
6. `state?since=<上次 version>` → 304；
7. `/health.holds` 在压站时出现该车与剩余秒数；
8. 把 `dispatch.yml` 的 `dimensions[].index` 改错 → 服务启动应报 ERROR（强制桥模式直接退出码 2）。
