## 3. persistPath：反射命中，但重启后仍然丢

重启后（同一份世界文件）：

```text
depot 1（线路头）  0a7783  planned=4ad410  lost=False   ← 未重生成，正常
depot 1（线路头）  9d163c  planned=4ad410  lost=False   ← 未重生成，正常
depot 2（线路中）  6b6eac  planned=''      lost=True    ← 本次重生成（lastPersist.ok=true）
depot 2（线路中）  a37272  planned=''      lost=True    ← 本轮【没有】被重生成
```

磁盘对比：`world/mtr/.../sidings` 与 `depots` 下所有文件与原始存档**字节大小完全一致**
（1974 / 4707 / 3413 / 3412），说明这次没有把存档写坏，问题在“写进去的路径宿主开机不认”。

结论（回答报告 §7.1 的判定）：**不是反射未命中**（`lastPersist.ok=true`、`method=writePathCache`），
而是 **writePathCache 返回成功但宿主重启后不采用**。

## 4. 回答 §7.2：路径丢失是按【车厂】传染的

本轮只对一个车厂的一条侧线（depot 2 的 6b6eac）做过重生成，但重启后 **depot 2 的两条侧线同时丢失**，
而 depot 1 的两条完全正常。这与 depot 归属完全吻合：

```text
depot 2（线路中）: a37272e024f03a0c, 6b6eacc355ec212f     ← 两条都 lost=True
depot 1（线路头）: 0a77836aaa2aac59, 9d163c32a64275f5     ← 两条都正常
```

上一轮 v1.6 里“未被直接操作的侧线也变 pathLost”，根因就在这里：**重生成的影响范围是车厂，不是侧线。**

## 5. 建议

### P1 · 让 persistPath 真正可验证

现在 `ok=true` 只代表反射调用没抛异常。建议改成“写完读回”：

```java
persistPath(siding);
Object after = Reflect.get(siding, "pathSidingToMainRoute");
// size > 0 才算 true；否则 lastPersist.ok=false 并写 lastError
```

并在 `writePathCache()` 之后立刻检查宿主的缓存文件是否出现（若可定位），把“写了但没生效”和“根本没写”分开。

### P1 · 以车厂为单位做恢复

既然影响是车厂级的，建议在启动时做一次**按车厂**的体检：

```text
if (某一车厂内任一停场车 pathLost=true) → 该车厂执行一次 depot 级重建（或提示运维执行）
```

单个侧线“只修自己”在当前实现下无法收口。

### P2 · 事件与计数已经够用

`/health.events` + `lastPersist` + `persistFailures` 这套组合本轮直接定位了问题，建议保持；
可以再加一个 `eventSeq`，方便调用方做增量拉取。
