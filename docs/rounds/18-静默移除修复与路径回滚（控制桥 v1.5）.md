# 18 · 静默移除修复与路径回滚（控制桥 v1.5）

对应报告：17-控制桥v1.4复测结果.md

产物：mtbridge/build/libs/mtbridge-1.5.0+1.20.1.jar（83,644 字节，reobf）
服务侧无改动。

---

## 1. 报告结论的确认

报告 §3 的静态定位是对的：三个移除点里，只有 “siding == null” 分支是静默的，
而实测组合（记录消失 + executed/failed/tickFailures 全不动）只与它吻合。
另外 §4 的发现更严重：每次探测都把侧线路径清空且不再恢复，四次之后四条车全部 planned="0"，
重启也不自愈。

本轮就针对这两件事：让移除不再静默，让清空可以回滚。

---

## 2. 修复 A：不再静默移除

改动（BridgeService.processRouteAttempts）：

    旧: Siding siding = simulator.sidingIdMap.get(attempt.sidingId());
        if (siding == null) { routeAttempts.remove(key); continue; }   // 无痕

    新: Siding siding = findSiding(simulator, attempt.sidingId());     // 线性扫描按 id
        if (siding == null) {
            // tick() 每维度跑一次，找不到通常意味着“这个侧线是别的维度的”
            if (now > attempt.deadline()) {                             // 60 s 硬上限
                remove; lastError = ...; recordTickError(...); fire(failed); failed++;
            }
            continue;                                                   // 否则保留，继续等
        }

三个关键点：

1. 用线性扫描而不是哈希查找：即使 key 空间有意外，也不会凭空返回 null；
2. “找不到”不再等于“删除”，而是“不是本维度”，跨维度 tick 因此不会互相清理；
3. 真到 60 s 仍找不到，才产生一次 failed + recordTickError，外部一定看得见。

其余移除点也全部留痕：

| 移除原因 | 计数 | 事件 | 记录 |
|---|---|---|---|
| 路径就绪 | executed++ | applied "path ready via 策略N" | — |
| 策略耗尽 | failed++ | failed（含 restored/ROLLBACK FAILED） | lastError |
| 超过 60 s 找不到侧线 | failed++ | failed "siding not found before deadline" | recordTickError |
| 处理中抛异常 | — | — | recordTickError("route: ...") |

## 3. 修复 B：路径快照与回滚

报告 §4 的根因：generateRoute 先清空、再生成；生成不出来就什么都不剩，重启也不会重建。

现在每次重生成前先快照三条路径，失败时写回：

    PathSnapshot snap = GameActions.snapshotPaths(siding);   // pathSidingToMainRoute / pathMainRoute / pathMainRouteToSiding
    ... generateRoute ...
    if (所有策略都失败) {
        boolean ok = GameActions.restorePaths(siding, snap);
        reason = "... " + (ok ? "; previous path restored" : "; ROLLBACK FAILED - siding has no outbound path");
    }

回滚写在宿主自己的列表对象上（clear + addAll），因此宿主后续 tick 直接用恢复后的路径。
若回滚也失败，会额外 recordTickError，并在车辆 JSON 里以 pathLost=true 暴露。

新增车辆字段：

    pathLost : true   // 停场车且 plannedFirstPlatformId == "0" —— 侧线没有出站路径

这条字段就是报告 §4 要求的那句“别让调用方以为只是没发车”。

## 4. 修复 C：诊断字段补齐

- /dispatch/v1/health 增加 lastTickError 与 routeDiag（上一轮只有 /state 有，报告 §2 指出了这点）；
- intent 过期、侧线意图因路径迟迟不就绪而放弃，都改为 recordTickError（不再只 +1 计数）；
- 同一错误消息只打一次 WARN，避免刷屏。

---

## 5. 重要：现有存档需要恢复一次

回滚只对“本版本之后”的重生成生效。报告 §4 里那四条车所在的侧线**已经被旧版本清空**，
需要任选一种方式恢复一次：

1. 游戏内：铁路仪表板 → 车厂 → 生成路线（宿主自己的重建入口）；
2. 或把 config/mtbridge.json 的 allowDepotRegeneration 设为 true，重启后对任一车发一次
   set_platform，让桥走策略 2（车厂级生成）——它会重建该车厂所有车的路径与时刻表。

恢复后 plannedFirstPlatformId 应回到非 "0"，pathLost 变 false。这一步不做，后续任何发车/选台
测试都会继续失败，但不是桥的问题。

---

## 6. 复测顺序

1. 先确认 pathLost=false / planned 非 "0"（若否，先做 §5 的恢复）；
2. 停场车 set_platform → routeDiag 应至少活过 3 s：
   - t+3s 仍在且 strategy 变 1 → 升级生效；
   - t+6s 仍未就绪且 allowDepotRegeneration=false → 应出现 failed 事件且 reason 含
     "previous path restored"（说明回滚成功，侧线没被毁）；
3. 打开 allowDepotRegeneration 再测 → 应看到 strategy 2 与（若成功）applied "path ready via 策略2"；
4. 路径就绪后再测 deploy_train（无目标）与 deploy_train(car, platform)。

需要回传：routeDiag（含 strategy 变化时序）、lastTickError、以及 failed 事件里的 reason 原文。

---

## 7. 仍未解决

- 策略 2 仍是破坏性的（重建整个车厂），保持默认关闭；
- 若策略 0/1 都不出路径且回滚成功，说明该目标平台与该侧线物理不连通——这是线网数据问题，
  需要换一个可达的站台，或者调整该车厂归属；
- 本地无法起真实服务端，本轮改动仍以“可观测 + 可回滚”为主，功能是否闭环取决于下一次真机复测。
