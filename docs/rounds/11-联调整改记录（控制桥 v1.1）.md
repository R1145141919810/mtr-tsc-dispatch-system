产物：`mtbridge/build/libs/mtbridge-1.1.0+1.20.1.jar`（70,110 字节，已 reobf）

## 1. P0 阻断级

### 1.1 启动时序竞态（桥永远不可用）

**根因**（与报告一致）：宿主在自己的 server-started 监听里才创建模拟器容器，桥的监听先跑就走到
`locate()` 拿到 null，之后不再重试。

**改动**（三处一起，不赌单一手段）：

```java
@SubscribeEvent(priority = EventPriority.LOWEST)   // 宿主的监听先执行
public void onServerStarted(ServerStartedEvent event) { host.tryAttach(server); ... }

// 每 tick 重试，直到就绪或明确放弃
private void retryLocate() {
    if (host.ready() || locateLogs >= MAX_LOCATE_LOGS) return;         // 12 次
    if (System.currentTimeMillis() < nextLocateAt) return;             // 5 s 间隔
    nextLocateAt = now + 5000;
    host.tryAttach(ServerLifecycleHooks.getCurrentServer());
    if (!host.ready()) LOGGER.info("waiting for host simulator {}/{} (locator={})", ...);
    else               LOGGER.info("simulators located after retry: {} ({})", ...);
    // 12 次仍失败 -> WARN，不再静默 ready=false 一整个会话
}
```

即使 LOWEST 那次仍然是 0，也会在 5 秒内被重试捞回来；重试计数在 `/mtbridge status` 的 `attempts=` 可见。

### 1.2 只 tick 维度 0

```java
for (int dimension = 0; dimension < host.dimensionCount(); dimension++) {
    Simulator simulator = host.simulator(dimension);
    if (simulator != null) service.tick(simulator);      // 每个维度的意图/压站都推进
}
```

## 2. P1 语义正确性

| 报告项 | 改动 | 现在的行为 |
|---|---|---|
| 4.3 意图挂 30 分钟 | 新增 per-command `ttlSeconds`（缺省取 `config.intentTtlSeconds=120`） | `set_platform` 意图 120 s 过期；`return_to_depot` 保留 900 s 下限（回场本身要跑完一趟） |
| 意图不可见 | `/dispatch/v1/health` 增加 `intents:[{vehicle,kind,target,source,createdAt,deadline}]` | 调用方能区分“还在排队”“已过期”“已执行” |
| 4.4 `return_to_depot` 忽略 target | 解析 `sidingId` 并与车辆自身侧线比对 | 指向别的股道 → `REJECTED "a train can only be held at its own siding <id>"`；参数不再是摆设 |
| 4.5 遥测缺三样 | 见下表 | 服务侧不再用“首次观测时刻”猜班次起点 |
| 4.6 坐标系混淆 | 新增 `currentStationId` / `nextStationId` / `nextPlatformId`，保留 `stationId` 作为 legacy 别名；`state` 与 `capabilities` 均带 `semantics: 2` | 调用方可按字段名区分“当前所在”与“下一停靠” |
| 4.7 无限压站 | `maxHoldSeconds`（默认 600）封顶，到期自动释放并计入 `autoReleased` | 调度服务崩溃也不会把车永久钉在站台 |

遥测新增字段：

| 字段 | 来源 | 说明 |
|---|---|---|
| `serviceStart` | 桥在车辆首次进入 `onRoute` 时记时，回库清零 | 桥重启会重置（内存态），但比“服务侧首次观测”准确 |
| `passengers` | `vehicleExtraData.iterateRidingEntities` 计数 | **下界**，同时给 `passengersExact:false`；TSC 不公开 NPC 乘客数 |
| `departure` | `eta + 下一停靠点 dwellTime` | 不再恒等于 `now` |

## 3. P2 协议与运维

| 项 | 改动 |
|---|---|
| `DEFERRED` 被缓存 600 s | 只缓存终态（APPLIED/REJECTED/FAILED/UNAVAILABLE）；`DEFERRED` 不入缓存，重试会重新评估，真实生效后立刻能拿到 `APPLIED` |
| `capabilities.dimensions` 只有数量 | 改为 `[{index, id}]`，id 取 `Simulator.dimension`（如 `minecraft/overworld`），顺序与宿主一致 |
| `state` 无版本 | 响应带 `version` 与 `ETag: "v<serverTime>"`；请求带 `If-None-Match` 命中返回 **304** |
| 503 分不清 | 世界未加载统一返回 `{"error":"loading","loading":true,...}` |
| 鉴权时序攻击 | `MessageDigest.isEqual` 常量时间比较 |
| 非回环 + 空 token 裸奔 | 启动时拒绝并打 ERROR 日志（fail closed） |
| HTTP 线程只有 2 个 | 默认 8（`httpThreads` 可配），状态轮询不再饿死指令 |
| 无演练模式 | `dryRun: true` 时所有指令返回 `APPLIED "dry-run: state untouched"`，不碰模拟器 |

## 4. 仍然做不到 / 未验证

1. **停到“别的”股道**：车辆只能回到它所属的侧线；跨股道需要重建那条侧线路径，而重建会清空该侧线
   在途车辆。现在改为**显式拒绝**，而不是静默忽略参数。
2. **乘客精确人数**：公共 API 只暴露乘车实体，NPC 乘客数不可得，因此 `passengersExact:false`。
3. **决策级真机回归**：本环境仍无 MTR 线网存档，未验证“选台/压站/回场”在真实车流下的效果——
   与报告 §5 的结论一致。

## 6. 上服自检清单（建议顺序）

1. 启动后看日志：应出现 `simulators located: 3 (...)`；若为 0 会出现 `waiting for host simulator n/12`，
   最多约 1 分钟后给出明确 WARN；
2. `GET /dispatch/v1/capabilities` → `dimensions:[{index:0,id:"minecraft/overworld"},{index:1,id:"minecraft/the_end"},...]`；
3. `GET /dispatch/v1/state?dimension=0` 带 `If-None-Match` 再请求 → 304；
4. 停一辆车在库，发 `{"kind":"deploy_train","vehicleId":"<id>","key":"t1"}` → `deferred`，1–2 s 内车动；
5. 对运行中的车发 `set_platform` → `deferred`，`health.intents` 里出现该车，TTL 到期后消失；
6. `dwell_control seconds:-1` → 车压住不走，10 分钟后自动释放（`autoReleased+1`）。
