## 1. 复测确认

主项通过：t+3.5s 路径就绪（策略 1）、t+4.9s 发车、t+5.6s 校验 applied "departed and verified on route"。
普通 deploy、dwell 无回归。上一轮的“延迟 1.5 s + 后置校验”成立。

一个附带发现：成功的是**策略 1**（generateRoute(platform, platform, 0)），策略 0 在该线网上依然产不出路径——
升级链路是必要的，不是摆设。

---

## 2. 关于 persistPath：不再试图“修写入”

报告的证据链很完整：

- lastPersist.ok=true、method=writePathCache（反射命中、调用未抛异常）；
- 重启后路径仍丢；
- 磁盘文件与原始存档**字节大小一致**（1974 / 4707 / 3413 / 3412）。

即：写调用发生了，但宿主重启后不采用这份缓存。这已经是宿主缓存格式/校验的问题，
桥无法从外部修复。所以本轮改变策略：

1. persistPath 改成**读回校验**：只有调用后路径仍在内存里才返回 true，否则 ok=false 并写 lastError；
2. 不再把“路径已持久化”当成恢复手段，改为**车厂级体检 + 重建**兜底。

---

## 3. 车厂级体检与恢复（本轮核心）

依据报告 §4：只重生成 depot 2 的一条侧线，重启后 depot 2 的两条侧线全丢，depot 1 的两条全好。
影响范围是车厂，所以恢复粒度也必须是车厂。

### 3.1 体检

    auditDepots(simulator):
        for depot in simulator.depotIdMap:
            lost  = [siding for siding in depot.savedRails if routeSegments(siding) == 0]
            parked = sum(vehicles(siding) for siding in depot.savedRails)
            if lost 非空 and parked > 0:
                记录 { depot, depotId, sidings, parkedTrains }

结果同时写入 /health.pathRecoveryNeeded，外部（含调度服务）可以据此只出 advisory。

### 3.2 恢复

| 方式 | 触发 | 说明 |
|---|---|---|
| 自动 | allowDepotRegeneration=true，每 10 s 巡检 | 每个车厂每会话只修一次，避免反复重建 |
| 手动 | /mtbridge recover | 对所有“有丢路径且有停场车”的车厂执行一次 |
| 查看 | /mtbridge audit | 只体检不重建 |

自动修复默认关闭：它是破坏性的（重建整个车厂、车辆 id 变化），必须由运维显式开启。
日志最多 60 s 一条，避免刷屏。

## 5. 复测建议

1. 重启后执行 /mtbridge audit → 应列出 depot 2（以及其中的侧线 id）；
2. /mtbridge recover → 再 audit 应为空，plannedFirstPlatformId 恢复为非 "0"；
3. 打开 allowDepotRegeneration 后重启 → 应自动修复，日志出现 “auto-recovered depot …”；
4. 若 persistPath 读回失败，/health.lastPersist.ok=false 且 lastError 有原文。

## 6. 仍未解决

宿主为什么不采用 writePathCache（缓存版本/校验字段未知）。桥现在不依赖它：
检测靠 auditDepots，恢复靠车厂级重建（手动或开关触发）。
若要在下一轮彻底解决，需要读宿主缓存文件的头部/版本字段，属于逆向宿主格式，
收益不大——车厂级重建已经能恢复可用状态。
