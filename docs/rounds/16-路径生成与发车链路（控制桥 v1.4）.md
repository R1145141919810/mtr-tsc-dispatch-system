## 1. 报告结论的确认

- P0（dwell_control 崩服）确实清零，本轮没有再动它。
- P1 的根因不是“发车时机”，而是报告 2.1 指出的那条：**generateRoute 之后侧线路径是空的**。
  证据是 plannedFirstPlatformId 从 4ad4105fad8390aa 变成 "0"、pathReady 恒 false。
  路径不存在时，后面所有 departureIndex 分支都不会被执行，所以上一轮修的发车逻辑“看起来没生效”。

本轮按报告建议的顺序改：先让路径真的生成，再谈发车。

## 2. 路径生成：三级策略 + 可观测

单次 generateRoute 不保证产出路径，而桥过去只调一次就宣称 deferred。
现在把生成做成一个有状态、可升级、可观测的尝试：

    策略 0: generateRoute(platform, null, -1, altitude)      ← 原实现
    策略 1: generateRoute(platform, platform, 0, altitude)   ← 报告建议的“不传 null”
    策略 2: Depot.generateDepots(simulator, [depot])          ← 车厂级，会重建时刻表，默认关闭

- 每次尝试后 3 s 检查 pathSidingToMainRoute 的段数；仍为 0 就升级到下一策略；
- 策略 2 受配置项 allowDepotRegeneration 控制（默认 false）：它会清空该车厂所有车，
  不适合由桥擅自决定；
- 全部策略用尽 → 发 failed 事件并写 lastError，不再静默挂着；
- 只有段数 > 0 才发 applied 事件（“path ready via 策略N”）。

新增观测字段（都在 /dispatch/v1/state 里）：

    routeDiag: [ { siding, platform, strategy, strategyName, startedAt } ]
    lastTickError: "<最近一条被吞掉的异常>"

于是“接受但永不生效”这种状态第一次变得可查：看一眼 routeDiag 就知道卡在哪个策略。

## 3. 发车：用真实时刻表索引，不造也不赌

上一轮 v1.3 的问题是走向另一个极端：只调 addDeparture(now)，把发车完全交给宿主，
结果宿主没有在下一 tick 调度（或时间表为空），车不动且不报错。

现在的做法是两步都做，但都以“真实索引”为准：

    long scheduled = Reflect.getLong(vehicle, "departureIndex");
    if (scheduled >= 0) { startUp(scheduled, now); applied; }        // 已有班次：提前发车

    int before = departures(siding).size();
    boolean added = siding.addDeparture(now);                        // 向侧线要一个班次
    if (!added && siding.area != null) {
        siding.area.generatePlatformDirectionsAndWriteDeparturesToSidings();  // 时间表被清空则重建
        added = siding.addDeparture(now);
    }
    List<Long> timetable = departures(siding);                       // 反射读取真实时刻表
    int index = (added && timetable.size() > before) ? timetable.size() - 1 : -1;
    if (index >= 0) {
        Reflect.setLong(vehicle, "departureIndex", index);           // 真实存在的索引
        Reflect.setLong(vehicle, "sidingDepartureTime", timetable.get(index));
        vehicle.startUp(index, timetable.get(index));
        applied "departed on timetable slot N";
    }

关键区别：索引来自 departures 列表本身（addDeparture 之后读回 size-1），
既不是硬编码 0，也不依赖宿主下一 tick 是否调度。startUp 用到的索引一定在表内，
宿主不会因为 “index >= departures.size()” 把车删掉。

失败分支会带回真实诊断：addDeparture 的返回值、时刻表条数、是否手动侧线。

## 4. tickFailures 现在能定位

报告指出 tickFailures=1 但 lastError 为空、日志无线索。现在：

- 每个被吞掉的异常都会写 lastTickError（类型 + 消息）并计入 tickFailures；
- 同一消息只向服务器日志打一次 WARN（去重集合），避免刷屏；
- /health 同时暴露 tickFailures 与 lastTickError，/state 也带一份。

## 5. 复测顺序（这次请严格按顺序，每步都看字段）

1. 停场车 set_platform 到另一站台 →
   看 routeDiag 是否出现 strategy 0；3 s 后策略升级则看 strategy 是否变 1；
   验收：plannedFirstPlatformId 变成目标台（非 "0"）。
2. 若 1 在策略 1 之后仍失败 → 在 config/mtbridge.json 打开 allowDepotRegeneration: true，
   重启后重复 1；此时会走策略 2（会重建整个车厂，注意会短暂影响该车厂其他车）。
3. 路径就绪后（plannedFirstPlatformId 有效）再测 deploy_train(无目标) →
   验收：onRoute=true、pathReady=true、车动。
4. 再测 deploy_train(car, platform)（重建 + 发车组合）。
5. dwell_control 复测（应仍不崩，tickFailures 若 >0 现在能拿到 lastTickError）。

需要回传的：routeDiag 内容、lastTickError、以及若策略 2 也失败时服务器日志里
SidingPathFinder 的 “Path not found” 行（那说明目标平台与该侧线不连通，是数据问题不是桥的问题）。
